Convolutional Networks

A convolution is a dot product wearing a sliding-window costume — see that clearly, and you can derive the shape of every layer in a CNN by hand.

30 min read You'll learn: convolution as an operation · output-shape math · pooling · ResNets & skip connections

Every image is a grid of numbers, so in principle you could feed it into the fully-connected layers from Section 1 — flatten the grid into one long vector and multiply by a big matrix. In practice this is a bad idea, for reasons that turn out to be exactly the reasons convolutional networks exist. Once you see why fully-connected layers struggle with images, the convolution operation stops looking like a new trick and starts looking like the obvious fix.

◆ The one idea to hold onto

A convolution takes one small, reusable pattern-detector (a kernel) and slides it over every position in the input, asking the same question everywhere: “how much of my pattern is here?” Reusing the same detector everywhere is what makes CNNs both cheap (few parameters) and smart about images (a cat is a cat wherever it appears).

1Why fully-connected layers struggle with images

Intuition first

A fully-connected layer gives every input pixel its own private weight, for every output neuron. That has two consequences, and both are bad for images. First, images have a lot of pixels, so the weight matrix becomes enormous. Second — and this is the subtler problem — the layer has no idea that “a cat's ear near the top of the photo” and “a cat's ear near the bottom of the photo” are the same feature. It learns them as two unrelated facts, because they land on two different input slots with two different weights.

☂ Everyday parallel

Imagine teaching someone to spot a stop sign by pointing at one photo and saying “the stop sign is the red octagon in the upper-left corner of this exact photo.” Show them a second photo where the sign has moved to the bottom-right, and they're lost — they never learned “stop sign,” they learned “red shape at one specific pixel location.” A fully-connected layer learns the same way: a separate weight per position, with nothing forcing it to reuse what it learned about a shape when that shape shows up somewhere else.

Now the math

Take a small colour image: 224×224 pixels, 3 colour channels (red, green, blue). Flattened into a vector, that's:

$$ 224 \times 224 \times 3 = 150{,}528 \text{ numbers} $$

In words: one single image is already a vector with over 150,000 entries. Connect that vector to a modestly sized hidden layer of just 1,000 neurons with a fully-connected layer, and the weight matrix W needs shape (150,528 × 1,000) — over 150 million numbers to learn, for one layer, before the network has looked at a single example. And every one of those weights is tied to one exact pixel position.

Convolution fixes both problems with one move: instead of a giant matrix that touches every pixel once, use a tiny matrix (the kernel) that touches every pixel many times, once per position it slides to. The next section makes that precise.

Check yourself Why does a fully-connected layer need to learn "cat ear near top" and "cat ear near bottom" as two separate things, when a human clearly doesn't? Reveal

Because a fully-connected layer's weights are indexed by input position: the weight connecting "pixel (10, 10)" to a given output neuron is a completely different number from the weight connecting "pixel (200, 200)" to that same neuron. Nothing in the layer says these two weights should be related, so the network must independently discover the "ear" pattern at every position it might appear — wasting both parameters and training data. A mechanism that reuses the same small detector at every position (a convolution) sidesteps this entirely.

2Convolution: a sliding dot product

Intuition first

A kernel (also called a filter) is a small grid of numbers — say 3×3. To apply it, you place it in the top-left corner of the input, multiply it elementwise against the patch of input underneath it, and add up the products into a single number. That's exactly a dot product (Section 1), just computed on a 2D patch instead of a flat list. Then you slide the kernel one step over and repeat, and again, until you've swept the whole input. The result is a new grid — one number per position — telling you how strongly that pattern showed up there.

☂ Everyday parallel

Picture searching a photo by sliding a small stencil or rubber stamp over it, checking at every position how well the stamp's shape lines up with what's underneath. Move the stencil one inch right, check again. Slide it down a row, check the whole row again. You never redraw the stencil — it's the same small shape, reused at every spot — you're just asking “does this pattern match here?” over and over across the whole page.

Now the math

Three numbers control how a convolution slides:

Definitions

The kernel size K is the width (and height) of the small sliding grid of weights. The stride S is how many pixels the kernel jumps between positions (stride 1 = check every pixel; stride 2 = skip every other one). Padding P is a border of zeros added around the input so the kernel can also center itself near the edges, and so you can control how much the output shrinks.

Let's derive how large the output grid comes out, for an input of width W (assume a square input and kernel for simplicity — the same formula applies to height). First, padding adds P zeros on each side, so the effective width becomes W + 2P. The kernel's left edge can start at position 0, then S, then 2S, and so on — the last legal starting position is the largest one where the kernel still fits inside the (padded) input:

$$ \begin{aligned} \text{start} + K &\le W + 2P \\ \text{start} &\le W + 2P - K \end{aligned} $$

In words: the kernel's starting position, plus its own width K, can't run past the padded edge. That caps how far right the kernel is allowed to start.

The starting positions are 0, S, 2S, … up to that cap, so the count of valid positions — which is exactly the output size — is that cap divided by the stride, plus one for the starting position itself:

$$ \text{out} = \left\lfloor \frac{W - K + 2P}{S} \right\rfloor + 1 $$

In words: take the input width, subtract the kernel width, add back twice the padding, divide by the stride, round down (⌊⌋ means “round down” — you can't have a fractional position), then add 1 to count the first position. This one formula tells you the exact output shape of any convolution before you run it.

Worked example

An input of width W = 7, kernel K = 3, stride S = 2, no padding (P = 0):

$$ \text{out} = \left\lfloor \frac{7 - 3 + 0}{2} \right\rfloor + 1 = \lfloor 2 \rfloor + 1 = 3 $$

In words: the kernel fits at starting positions 0, 2, and 4 (covering pixels 0–2, 2–4, and 4–6) — three positions, three output values, matching the formula.

A second, very common case: keeping the output the same size as the input (“same” padding), with W = 5, K = 3, S = 1, P = 1:

$$ \text{out} = \left\lfloor \frac{5 - 3 + 2}{1} \right\rfloor + 1 = 4 + 1 = 5 $$

In words: with a 3×3 kernel, padding of 1 on each side exactly cancels the 2-pixel shrinkage a 3-wide kernel would otherwise cause, so the output stays 5×5. This is why you'll so often see “kernel 3, padding 1” paired together in real architectures.

Channels, feature maps, and parameter sharing

A colour image doesn't have one grid of numbers — it has three (red, green, blue), called channels. A kernel for such an input isn't 3×3, it's 3×3×3: it spans the full depth of the input and produces one number per position by summing over all three channels at once. One kernel produces one output grid, called a feature map — a map of “how much did my pattern fire, at every position.” A convolutional layer normally learns many kernels in parallel (say, 64 of them), producing 64 stacked feature maps — which then become the 64 input channels for the next layer.

◆ Parameter sharing

The crucial trick: the same kernel weights are reused at every position in the image. This single choice buys two things at once. It gives translation invariance — a pattern the kernel learned to detect in one corner is automatically detected anywhere else, since it's the same weights doing the checking. And it slashes the parameter count: a 3×3 kernel over 3 input channels producing 64 output feature maps needs $3\times3\times3\times64 = 1{,}728$ weights — regardless of whether the image is 32×32 or 3200×3200. Compare that to the 150-million-weight fully-connected layer from the start of this section: convolution is doing more useful work with four orders of magnitude fewer numbers.

The same thing in PyTorch

nn.Conv2d and the shape formula in action

import torch
import torch.nn as nn

# batch of 8 RGB images, 32x32 pixels: shape (batch, channels, height, width)
x = torch.randn(8, 3, 32, 32)

conv = nn.Conv2d(in_channels=3, out_channels=16, kernel_size=3, stride=1, padding=1)
y = conv(x)
print(y.shape)  # torch.Size([8, 16, 32, 32])
# height/width: floor((32 - 3 + 2*1)/1) + 1 = 32  -> "same" padding, confirmed
# channels: 16, one feature map per learned filter

print(conv.weight.shape)  # torch.Size([16, 3, 3, 3]) -> (out_ch, in_ch, K, K)
print(sum(p.numel() for p in conv.parameters()))  # 16*3*3*3 + 16 bias = 448

# a downsampling conv: stride 2, no padding
down = nn.Conv2d(3, 16, kernel_size=3, stride=2, padding=0)
print(down(x).shape)  # torch.Size([8, 16, 15, 15])
# floor((32 - 3 + 0)/2) + 1 = floor(29/2) + 1 = 14 + 1 = 15
Check yourself An input feature map is 28×28. You apply a convolution with kernel size 5, stride 1, and padding 2. What is the output size, and how many weights does one such filter have if the input has 8 channels? Reveal

Output size: floor((28 − 5 + 2·2)/1) + 1 = floor(27/1) + 1 = 27 + 1 = 28 — padding of 2 with a 5-wide kernel again gives "same" padding, so the output stays 28×28. One filter spanning 8 input channels has 5 × 5 × 8 = 200 weights (plus 1 bias), no matter how large the 28×28 map is — that independence from spatial size is the whole point of parameter sharing.

3Pooling: shrinking on purpose

Intuition first

After a few convolutions you often want to shrink the feature maps deliberately — fewer numbers to carry forward, and a little tolerance for the exact pattern shifting by a pixel or two. Pooling does this with no learned weights at all: it slides a small window over the input and, at each position, keeps just one summary number.

☂ Everyday parallel

Think of a company town-hall: instead of forwarding every employee's individual comment up the chain, each team submits a single summary. Max pooling is a team forwarding its loudest, strongest opinion (the maximum value in the window) — great for asking “did this pattern show up anywhere in this neighbourhood?” Average pooling is a team forwarding its average sentiment (the mean of the window) — a smoother, less spiky summary.

Now the math

Pooling uses the exact same sliding mechanics as convolution — and the exact same output-size formula from earlier — but with kernel size K and stride S usually set equal (so windows don't overlap), and no weights: the operation itself, not learned numbers, decides the output.

$$ \text{out} = \left\lfloor \frac{W - K + 2P}{S} \right\rfloor + 1 $$

In words: same formula as convolution's output size, because pooling is structurally the same sliding-window operation — only the thing computed inside each window (max, or mean) differs.

The same thing in PyTorch

import torch
import torch.nn as nn

x = torch.randn(8, 16, 32, 32)

pool = nn.MaxPool2d(kernel_size=2, stride=2)
y = pool(x)
print(y.shape)  # torch.Size([8, 16, 16, 16])
# floor((32 - 2 + 0)/2) + 1 = 15 + 1 = 16, applied to height and width
Check yourself Why does 2×2 max pooling with stride 2 give a small amount of tolerance to the input shifting by one pixel, while a plain matrix multiply wouldn't? Reveal

Inside each 2×2 window, max pooling only cares which value is largest, not exactly where it sits within that window. So if the whole feature map shifts by a pixel, a strong activation that used to be, say, top-left of its window is now top-right of the same window — and max pooling still reports the same maximum. A fully-connected or purely positional operation has no such slack: every input slot maps to a fixed, distinct weight, so a one-pixel shift changes which weights get multiplied by what, and the output changes too.

4ResNets and skip connections

Intuition first

Once researchers had convolutions, the obvious next move was to stack more of them — deeper networks should be strictly more powerful, since a deep network can always just copy the input through unchanged if extra layers aren't helping. But in practice, plain stacks of convolutions got harder to train past a certain depth, and not because of overfitting — even training accuracy got worse. The culprit is the same one from Section 1's eigenvalue discussion and Section 12: gradients have to flow backward through every layer, and if each layer shrinks the gradient a little, dozens of layers shrink it to essentially zero — the vanishing gradient problem. Early layers stop learning because barely any error signal reaches them.

☂ Everyday parallel

Picture a long road with a set of traffic lights at every block. If each light only lets 80% of cars through, by block 50 almost no car from the start of the road has made it to the end — not because the road is broken, just because the effect compounds. Now add an express lane that runs alongside the whole road, letting some traffic skip every light entirely and arrive untouched. Even if the light-by-light lane is badly congested, the express lane guarantees traffic still gets through. A skip connection is that express lane, for gradients.

Now the math

A plain layer computes some function of its input, F(x), and passes only that forward. A residual block instead computes:

$$ y = x + F(x) $$

In words: F(x) (a couple of convolutions) still gets computed and still gets used, but it's added to the original input x rather than replacing it. If F learns nothing useful, F(x) ≈ 0 and the block simply passes x through untouched — the identity is always available as a fallback, which is exactly the “deeper should never hurt” property plain stacks failed to get in practice.

Here's why this fixes the gradient problem. During backpropagation (see Section 12) we need the derivative of the output y with respect to the input x, by the chain rule:

$$ \frac{\partial y}{\partial x} = \frac{\partial x}{\partial x} + \frac{\partial F(x)}{\partial x} = I + \frac{\partial F}{\partial x} $$

In words: the gradient splits into two paths, added together: an identity path (I, exactly 1 — the derivative of x with respect to itself) and whatever the convolutions inside F contribute. Stack many residual blocks and the gradient through the whole stack is a product of terms that each look like $(I + \partial F/\partial x)$. Even if every $\partial F/\partial x$ is tiny or poorly scaled, the “1 +” guarantees each factor stays close to 1 instead of collapsing toward 0 — so the gradient signal reaches early layers largely intact. This is the same shrink-or-explode story as repeated matrix multiplication in Section 1's eigenvalue example and the recurrent networks in Section 17; the skip connection is a structural fix rather than a tuning fix.

The same thing in PyTorch

a minimal residual block

import torch
import torch.nn as nn

class ResidualBlock(nn.Module):
    def __init__(self, channels):
        super().__init__()
        self.conv1 = nn.Conv2d(channels, channels, kernel_size=3, padding=1)
        self.conv2 = nn.Conv2d(channels, channels, kernel_size=3, padding=1)
        self.relu = nn.ReLU()

    def forward(self, x):
        out = self.relu(self.conv1(x))
        out = self.conv2(out)
        return self.relu(x + out)   # the skip connection: x + F(x)

block = ResidualBlock(channels=16)
x = torch.randn(8, 16, 32, 32)
y = block(x)
print(y.shape)  # torch.Size([8, 16, 32, 32]) -> padding=1, kernel=3 keeps size unchanged
Check yourself In a residual block y = x + F(x), suppose training has driven F's weights to nearly zero everywhere (the block hasn't found anything useful to add yet). What does the block output, and what is the gradient flowing back through it? Reveal

The output is y ≈ x + 0 = x: the block behaves like an identity function, passing its input through essentially unchanged — harmless, not broken. The gradient is ∂y/∂x = I + ∂F/∂x ≈ I: with F contributing almost nothing, the gradient passes through at essentially full strength (multiplied by 1), rather than being crushed by whatever a plain (non-residual) layer would have done. This is exactly why very deep ResNets can train at all: untrained or unhelpful blocks default to "do nothing" instead of "actively destroy the signal."

5What to carry forward

  • Fully-connected layers give images too many parameters and no reuse of learned patterns across positions; convolution fixes both.
  • A convolution slides a small kernel over the input, computing a dot product at each position; output size follows $\lfloor (W-K+2P)/S \rfloor + 1$ — derive it, don't memorize it.
  • Parameter sharing (the same kernel reused everywhere) gives translation invariance and cuts parameter counts by orders of magnitude versus a fully-connected layer.
  • Pooling downsamples with no learned weights, using the same sliding-window formula, and adds a little shift tolerance.
  • Skip connections ($y = x + F(x)$) keep gradients flowing in very deep networks because the identity path contributes a "+1" that a shrinking $\partial F/\partial x$ can't cancel out.

Convolutions assume a grid with local structure — great for images, but text and audio have a different structure: order along a single sequence. Next we'll see how networks handle that.
