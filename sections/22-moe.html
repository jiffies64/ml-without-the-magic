Mixture of Experts from Scratch

The technique behind today's biggest models — build the router, derive the balancing loss, and swap it into the transformer you already understand.

46 min read
You'll learn
  • conditional computation
  • top-k router math
  • the load-balancing auxiliary loss (derived)
  • a full annotated MoE transformer, dense vs MoE

Every model you have built so far runs all of its weights on every input. A bigger model means more weights, and more weights means more arithmetic per token — the cost and the capacity are chained together. This lesson breaks that chain. A Mixture of Experts (MoE) lets you grow the number of parameters a model owns without growing the amount of work it does per token. It is the single idea that lets a model carry hundreds of billions of parameters while only touching a few billion for any given word. We will derive it fully and build a working one.

◆ The one idea to hold onto

A dense layer asks every parameter about every token. An MoE layer keeps many separate sub-networks (the experts) but a tiny router sends each token to only a few of them. Total knowledge goes up; work per token stays flat. The whole lesson is about building that router and stopping it from cheating.

This is the capstone: it leans on the transformer block from Section 18 and the next-token training setup from Section 19. If those are fresh in your mind, everything here will click into place, because an MoE changes exactly one sub-layer of the block you already know.

1Conditional computation: pay for what you use

Intuition first

Here is the tension. Bigger models are smarter — that is one of the most reliable findings in machine learning. But in a normal (dense) network, "bigger" means every input runs through every weight, so doubling the parameters roughly doubles the compute (the arithmetic work) for every single token. That gets expensive fast. Conditional computation is the escape hatch: instead of running the whole network on each token, run only the part of the network that is relevant to that token. Most weights stay asleep for most inputs.

☂ Everyday parallel

Walk into a large hospital with a broken wrist. You do not get examined by all three hundred doctors on staff. The front desk (a router) glances at your problem and sends you to the orthopaedist. The hospital's total expertise is enormous — cardiology, neurology, paediatrics, all of it — but your visit only spends the time of one or two specialists. The building can keep hiring more specialists without making each patient's visit any longer. That is conditional computation: a huge amount of available skill, but each case only touches the relevant slice.

Now the math

Let a single expert sub-network cost $C$ units of compute to run on one token. Put $N$ of these experts side by side and let the router send each token to $k$ of them (with $k \ll N$, read "k is much smaller than N"). Then:

$$ \text{Total parameters} \;\propto\; N\,C, \qquad \text{Compute per token} \;\propto\; k\,C $$

In words: the knowledge you store scales with the number of experts N, but the work you do per token scales only with how many you actually use, k. Set N = 64 experts and k = 2, and you own 32× the parameters of one expert while doing only 2× the work. The two numbers, once chained together in a dense model, are now decoupled.

Definition

A model's active parameters are the weights that actually take part in processing a given token; its total parameters are all the weights it stores. In a dense model these two numbers are equal. The entire promise of MoE is to make total parameters large while keeping active parameters small.

◆ Why this matters right now

Almost every frontier model of the last few years is a sparse MoE under the hood. The reason is exactly the equation above: they behave like a model with a trillion parameters' worth of knowledge, but each token only pays for a few tens of billions. You are about to build the mechanism that makes that possible.

Check yourself You have an MoE layer with N = 8 experts, each identical to a dense feed-forward block, and you route each token to k = 2 of them. Compared with a single dense feed-forward block, how many times more parameters does the layer store, and how much more compute does it do per token? Reveal

It stores 8× the parameters (eight full copies of the block, one per expert), plus a tiny router. But it only runs 2 of those blocks on any given token, so it does about 2× the compute per token — not 8×. That gap between 8× the knowledge and 2× the cost is the whole point. The router's own cost is negligible: it is a single small matrix, which we size next.

2Where the experts go: one swapped sub-layer

Intuition first

Recall the transformer block from Section 18. Each block has two sub-layers: a self-attention sub-layer (where tokens look at each other and mix information) and a feed-forward network (FFN — a small two-layer network applied to each token on its own). The FFN is where most of a transformer's parameters live and where most of its raw "thinking per token" happens. MoE makes one surgical change: replace that single FFN with a set of FFNs plus a router. Attention is left completely untouched.

☂ Everyday parallel

Think of a busy kitchen. The prep station where everyone shares ingredients and passes plates around — that is attention, and it stays exactly as it was. But the single all-purpose cook who used to handle every dish (the FFN) is replaced by a row of specialist cooks: one for sauces, one for grilling, one for desserts. A tiny expediter at the pass reads each ticket and hands it to the right specialist. Same kitchen, same flow of plates — we only swapped one generalist for a routed team.

So the block goes from this:

$$ \mathbf{x} \;\to\; \mathbf{x} + \text{Attention}(\mathbf{x}) \;\to\; \mathbf{x} + \text{FFN}(\mathbf{x}) $$

to this — with only the second step changed:

$$ \mathbf{x} \;\to\; \mathbf{x} + \text{Attention}(\mathbf{x}) \;\to\; \mathbf{x} + \text{MoE}(\mathbf{x}) $$

In words: the + is the residual connection (add the sub-layer's output back onto its input, from Section 18). Everything is identical except that the fixed FFN is now an MoE block that, internally, will pick a few experts per token instead of running one shared network. From the outside, the block still takes a vector of shape d_model in and returns one of the same shape.

Definition

An expert is just an ordinary FFN — the same two-layer network the dense block used. There is nothing special inside an expert; the intelligence comes from the router learning to send different kinds of tokens to different experts, so each expert can quietly specialize. We build the expert first because it is the part you already know.

The same thing in PyTorch

an expert is a plain feed-forward block

import torch
import torch.nn as nn
import torch.nn.functional as F

class Expert(nn.Module):
    """One expert = the standard transformer FFN: expand, nonlinearity, project back."""
    def __init__(self, d_model, d_ff):
        super().__init__()
        self.up   = nn.Linear(d_model, d_ff)   # widen d_model -> d_ff
        self.down = nn.Linear(d_ff, d_model)   # narrow d_ff  -> d_model

    def forward(self, x):
        # x: (num_tokens, d_model)  ->  (num_tokens, d_model)
        return self.down(F.gelu(self.up(x)))

In words: exactly the FFN from a normal transformer — a wide hidden layer (d_ff, usually 4× d_model), a GELU nonlinearity (a smooth activation function; see Section 9), and a projection back to d_model. An MoE layer will hold N of these in a list.

Check yourself Why do we replace the FFN sub-layer with experts, and not the attention sub-layer? Reveal

Two reasons. First, the FFN is where the bulk of a transformer's parameters and per-token compute sit, so it is the sub-layer worth making sparse. Second, the FFN treats each token independently — it maps one vector to one vector — which makes routing natural: you can send each token to its own expert without breaking anything. Attention, by contrast, is all about tokens mixing with each other; routing tokens to separate experts there would cut those connections. So we keep attention dense and make the position-wise FFN sparse.

3The router: top-k gating, derived

Intuition first

The router (also called the gating network) is the front desk. For each token it must answer two questions: which experts should handle this token, and how much should each of them count? It answers with a small learned matrix, a softmax, and a "keep only the top few" step. That is the entire router — a single linear layer followed by a selection rule. Let's build it symbol by symbol.

☂ Everyday parallel

You describe your symptoms at the front desk. The receptionist mentally scores every department — "80% orthopaedics, 15% general, 5% neurology" — then sends you to the top one or two, and tells the ward how confident they are ("mostly orthopaedics, a little general"). The scores are the routing probabilities; keeping the top one or two is top-k selection; and passing along the confidence so the wards can blend their opinions is the weighting. The router does all three.

Now the math

Take a single token's vector $\mathbf{x}_t \in \mathbb{R}^{d}$ (here $d = d_{\text{model}}$, and $t$ indexes the token). The router owns one weight matrix $\mathbf{W}_g \in \mathbb{R}^{d \times N}$, where $N$ is the number of experts. Step 1 — gate logits. Multiply to get one raw score per expert:

$$ \mathbf{g}_t \;=\; \mathbf{x}_t\,\mathbf{W}_g \;\in\; \mathbb{R}^{N} $$

In words: gt is a list of N numbers, one per expert — the "raw affinity" of this token for each expert. These are called logits: raw scores, not yet probabilities (they can be negative and do not sum to anything in particular). The router matrix Wg is tiny: d × N, which for d = 512, N = 8 is about four thousand numbers — nothing next to an expert.

Step 2 — routing probabilities. Turn the raw scores into probabilities with a softmax (a function that squashes a list of numbers into positive values that sum to 1; see Section 4):

$$ p_{t,i} \;=\; \operatorname{softmax}(\mathbf{g}_t)_i \;=\; \frac{\exp(g_{t,i})}{\sum_{j=1}^{N} \exp(g_{t,j})} $$

In words: pt,i is the probability the router assigns to expert i for token t. Exponentiating makes every score positive; dividing by the sum makes them add up to 1. Now we have a clean "how much does this token belong to each expert" distribution, e.g. [0.6, 0.25, 0.1, 0.05, …].

Step 3 — top-k selection. Running all N experts would defeat the purpose. So we keep only the $k$ experts with the highest probabilities. Write that chosen set as $\mathcal{S}_t$:

$$ \mathcal{S}_t \;=\; \operatorname*{top\text{-}k}_{\,i}\; p_{t,i} \quad\text{(the } k \text{ experts with the largest } p_{t,i}) $$

In words: St is the short list — for k = 2, the two experts this token scored highest. Every expert outside St is switched off for this token and does zero work. This selection step is exactly where the "sparse" in "sparse MoE" comes from.

Step 4 — renormalize the survivors. The kept probabilities no longer sum to 1 (we threw the rest away). If they summed to, say, 0.85, we would be quietly scaling this token's contribution down by 15%. So we divide by their own sum to restore a clean weighting:

$$ w_{t,i} \;=\; \frac{p_{t,i}}{\displaystyle\sum_{j \in \mathcal{S}_t} p_{t,j}} \qquad \text{for } i \in \mathcal{S}_t $$

In words: wt,i is the final weight for expert i on token t. After this step the chosen weights sum to exactly 1, so the experts' outputs get blended, not shrunk. If k = 2 and the top two probabilities were 0.6 and 0.25, the renormalized weights are 0.6 / 0.85 ≈ 0.706 and 0.25 / 0.85 ≈ 0.294.

Step 5 — combine. Run the token through each chosen expert and add up their outputs, weighted by $w_{t,i}$:

$$ \mathbf{y}_t \;=\; \sum_{i \in \mathcal{S}_t} w_{t,i}\;\, E_i(\mathbf{x}_t) $$

In words: Ei is expert i (an FFN). The output yt is a weighted average of just the k chosen experts' answers. Experts the router trusted more get a bigger say. This one line is the whole forward pass of an MoE layer — the rest of the code is just doing it efficiently for a whole batch at once.

◆ Why the router can learn at all

The weights $w_{t,i}$ multiply the experts' outputs, so gradients (from backprop) flow back through them into $\mathbf{W}_g$. If sending a token to expert 3 lowered the loss, the router is nudged to raise $p_{t,3}$ next time. The hard "pick the top k" step itself is not differentiable, but because the kept experts are weighted by their soft probabilities, the router still gets a gradient signal through the survivors. That is why top-k gating trains end-to-end with plain gradient descent.

The same thing in PyTorch

router: linear → softmax → top-k → renormalize (returns aux loss too — derived next)

class Router(nn.Module):
    """Scores each token over N experts, keeps the top-k, and renormalizes their weights."""
    def __init__(self, d_model, num_experts, k, aux_alpha=0.01):
        super().__init__()
        self.gate = nn.Linear(d_model, num_experts, bias=False)  # W_g : (d_model, N)
        self.num_experts = num_experts
        self.k = k
        self.aux_alpha = aux_alpha

    def forward(self, x):
        # x: (num_tokens, d_model)
        logits = self.gate(x)                      # (num_tokens, N)  -> gate logits g
        probs  = logits.softmax(dim=-1)            # (num_tokens, N)  -> routing probs p

        # top-k experts per token
        topk_probs, topk_idx = probs.topk(self.k, dim=-1)   # each (num_tokens, k)
        # renormalize the survivors so their weights sum to 1
        topk_weights = topk_probs / topk_probs.sum(dim=-1, keepdim=True)

        aux_loss = self._load_balancing_loss(probs, topk_idx)  # derived in section 4
        return topk_idx, topk_weights, aux_loss

In words: the four math steps map one-to-one onto four lines. topk returns both the kept probabilities and the indices of the experts they belong to. Dividing by topk_probs.sum(...) is the renormalize step. We defer the aux_loss helper to the next section, where we derive exactly what it computes.

Check yourself A token's softmax over 4 experts is [0.5, 0.3, 0.15, 0.05] and we use k = 2. Which experts are chosen, and what are their final (renormalized) weights? Reveal

The top two probabilities are 0.5 (expert 0) and 0.3 (expert 1), so S = {0, 1}. Their sum is 0.8, so the renormalized weights are 0.5 / 0.8 = 0.625 and 0.3 / 0.8 = 0.375. Experts 2 and 3 are switched off for this token. Notice the weights now sum to exactly 1: the token's output is a genuine blend, 0.625·E₀(x) + 0.375·E₁(x), not a faded-out version.

4Load balancing: deriving the auxiliary loss

Intuition first

Left alone, the router cheats. Early in training one expert happens to be slightly better, so the router sends it slightly more tokens, so it trains faster and gets even better, so the router sends it even more tokens. This is a rich-get-richer feedback loop (also called routing collapse): a handful of experts hog everything and the rest never receive enough tokens to learn. You paid for N experts and got 2. We need a gentle force that keeps the traffic spread out.

☂ Everyday parallel

One doctor at the clinic gets a great reputation. Everyone asks for them, so their queue grows to three hours while four other perfectly good doctors sit in empty rooms. The clinic is underused and the famous doctor is overwhelmed. The fix is a scheduling rule that nudges patients toward the idle doctors — not forcing it, just tilting the odds so the whole staff stays busy. The auxiliary loss is that scheduling rule, written as math and added to training.

Definition

An auxiliary loss is an extra term added to the training loss that does not measure task performance directly, but instead pushes some internal quantity toward a desired shape. Here it pushes the token traffic toward being spread evenly across experts. The model minimizes task loss + auxiliary loss together.

Now the math

We want to measure, and then punish, imbalance. Over a batch of $T$ tokens we define two quantities per expert $i$. The first is a hard count — what actually got routed:

$$ f_i \;=\; \frac{1}{T} \sum_{t=1}^{T} \mathbb{1}\big[\, i \in \mathcal{S}_t \,\big] $$

In words: fi is the fraction of tokens routed to expert i. The symbol 𝟙[·] is the indicator: it is 1 when the condition inside is true and 0 otherwise. So we count how many tokens picked expert i in their top-k, and divide by the number of tokens. This is a hard, discrete count — you either got the token or you did not.

The second is a soft average — how much probability the router wanted to give each expert, before the hard cutoff:

$$ P_i \;=\; \frac{1}{T} \sum_{t=1}^{T} p_{t,i} $$

In words: Pi is the mean router probability for expert i, averaged over all tokens — using the full softmax pt,i, not just the chosen ones. It is smooth and differentiable, which will matter in a moment. Think of fi as "who actually walked in" and Pi as "how much the receptionist leaned toward this department on average".

The Switch Transformer auxiliary loss multiplies these two, sums over experts, and scales:

$$ L_{\text{aux}} \;=\; \alpha \, N \sum_{i=1}^{N} f_i \, P_i $$

In words: α (alpha) is a small weighting coefficient (typically 0.01); N is the number of experts, included so the loss's natural size does not shrink as you add experts. The heart of it is Σ fi Pi: a dot product between the hard load and the soft preference. We now show why minimizing it forces balance.

Why minimizing $\sum_i f_i P_i$ spreads the load

Two facts pin it down. First, both quantities are (near) probability distributions over the experts. For $k = 1$ each token picks exactly one expert, so the fractions sum to one, and the probabilities always do:

$$ \sum_{i=1}^{N} f_i \;=\; 1, \qquad \sum_{i=1}^{N} P_i \;=\; 1 $$

Second, on average a token that the router prefers (high $P_i$) is also a token it routes there (high $f_i$) — the count is just the hard version of the preference. Treat them as tracking each other, $f_i \approx P_i$, for the purpose of seeing what we are minimizing. Then the objective becomes:

$$ \sum_{i=1}^{N} f_i \, P_i \;\approx\; \sum_{i=1}^{N} P_i^{\,2} $$

Now we minimize $\sum_i P_i^2$ subject to $\sum_i P_i = 1$. By the Cauchy–Schwarz inequality (or just the fact that spreading mass reduces the sum of squares):

$$ \Big(\sum_{i=1}^{N} P_i \cdot 1\Big)^{2} \;\le\; \Big(\sum_{i=1}^{N} P_i^{2}\Big)\Big(\sum_{i=1}^{N} 1^{2}\Big) \;\;\Longrightarrow\;\; 1 \;\le\; N \sum_{i=1}^{N} P_i^{2} $$ $$ \sum_{i=1}^{N} P_i^{2} \;\ge\; \frac{1}{N}, \qquad \text{with equality iff } P_i = \tfrac{1}{N}\ \text{for all } i $$

In words: the sum of squares is smallest exactly when every expert gets the same share, 1/N. A lopsided distribution (one expert at 0.9) has a big sum of squares; a flat one (all at 1/N) has the smallest possible. So driving Σ fi Pi down literally pushes the routing toward the uniform 1/N split — every expert busy, none idle. Plugging the balanced value back in, Laux = α·N·(1/N) = α: at perfect balance the penalty bottoms out at just α, so a balanced router pays almost nothing.

◆ The clever part: which factor gets the gradient

The count $f_i$ comes from a hard top-k pick, so it has no usable gradient — you cannot smoothly differentiate "was this token in the top 2?". The probability $P_i$ is a smooth softmax average, so it does. In the product $f_i P_i$, the gradient flows through $P_i$ while $f_i$ acts as a fixed weight. The effect: experts that are currently overloaded (big $f_i$) get their probability $P_i$ pushed down hardest, which steers the next batch's tokens toward the quiet experts. The hard count decides who gets penalized; the soft probability is how the penalty is applied.

The coefficient $\alpha$ is a dial with a real trade-off. Too small and the balancing force is too weak to stop collapse — you drift back to a few favourite experts. Too large and you overpower the task loss: the router is forced to spread tokens uniformly regardless of whether that is good for the actual prediction, which hurts quality. The standard value $\alpha = 0.01$ keeps balance without drowning out the thing you actually care about.

The same thing in PyTorch

the load-balancing loss, exactly as derived

    def _load_balancing_loss(self, probs, topk_idx):
        # probs:    (num_tokens, N)  full softmax routing probabilities
        # topk_idx: (num_tokens, k)  indices of the experts each token selected
        num_tokens = probs.shape[0]

        # hard assignment mask: mask[t, i] = 1 if token t routed to expert i
        mask = torch.zeros_like(probs)
        mask.scatter_(1, topk_idx, 1.0)           # place 1s at the chosen experts

        f = mask.mean(dim=0)      # (N,)  fraction of tokens routed to each expert  -> f_i
        P = probs.mean(dim=0)     # (N,)  mean router probability per expert         -> P_i

        return self.aux_alpha * self.num_experts * (f * P).sum()

In words: scatter_ writes a 1 into the mask at each chosen (token, expert) spot, giving the hard assignment. Averaging that mask down the token axis is fi; averaging the raw probabilities is Pi; the final line is α·N·Σ fiPi verbatim. This returns a single scalar we will add to the task loss. (You can check by hand that a perfectly uniform split gives exactly α.)

▲ Watch out

Do not detach or torch.no_grad() the P = probs.mean(0) line — the whole point is that gradients flow through $P_i$ back into the router. It is fine that $f_i$ (built from the hard topk_idx) carries no gradient; that is by design. If you accidentally block the gradient on $P_i$, the auxiliary loss becomes a constant and does nothing, and your experts will quietly collapse.

Check yourself With 4 experts, a router collapses so that f = [1, 0, 0, 0] and P = [0.97, 0.01, 0.01, 0.01]. Is Σ fᵢPᵢ large or small, and how does it compare with a balanced router? Reveal

Collapsed: Σ fᵢPᵢ = 1·0.97 + 0 + 0 + 0 = 0.97. Balanced, where f = P = [0.25, 0.25, 0.25, 0.25]: Σ fᵢPᵢ = 4·(0.25·0.25) = 0.25. The collapsed router scores 0.97, almost four times the balanced 0.25 — and 0.25 = 1/N is the smallest the sum can be, exactly the minimum we proved. So the auxiliary loss is much larger under collapse, and gradient descent pushes hard to escape it. That is the balancing force doing its job.

5Capacity factor and token dropping

Intuition first

On real hardware, experts run in parallel, and a chip likes fixed-size chunks of work. But routing is uneven from batch to batch — sometimes one expert is asked to take far more than its fair share. To keep the work rectangular, each expert is given a fixed capacity: a maximum number of tokens it will accept this batch. Tokens beyond that limit are dropped — the expert skips them, and they pass through the layer unchanged via the residual connection.

☂ Everyday parallel

The specialist doctor can see, say, twenty patients this morning — that is their capacity. Send twenty-five and five get turned away at the door; they leave as they came (unchanged) and try again later. It is not ideal, but it keeps the schedule predictable so the hospital can run every room in lock-step instead of waiting on the one overloaded office.

Now the math

The per-expert budget is set by a capacity factor $c$ (a small multiplier, usually between 1.0 and 2.0):

$$ \text{capacity} \;=\; c \cdot \frac{T \cdot k}{N} $$

In words: T·k / N is the number of tokens each expert would get if the T tokens (each sent to k experts) were split perfectly evenly. The factor c adds slack: c = 1.25 means "accept up to 25% more than the fair share before dropping". A bigger c drops fewer tokens but wastes more compute on half-empty expert buffers; a smaller c is cheaper but drops more. The auxiliary load-balancing loss we built above is what keeps the traffic even enough that few tokens actually get dropped.

To keep the code in this lesson clear, our implementation does not impose a capacity limit — it processes every token — so you can see the routing logic without the bookkeeping. In production systems capacity matters a lot for speed; the good news is that a well-balanced router (which the auxiliary loss gives you) rarely overflows, so dropped tokens stay negligible.

▲ Watch out

Dropped tokens are a silent quality leak. If your capacity factor is too low and your router is imbalanced, a meaningful fraction of tokens skip the expert layer entirely and get only their residual — as if the FFN were switched off for them. If MoE quality is mysteriously poor, measure your drop rate before blaming the experts.

6The full MoE layer, in a transformer, training

Intuition first

We have every piece: the Expert, the Router with its auxiliary loss — all built in the sections above. Now we assemble the MoELayer that dispatches each token to its chosen experts and blends the results, drop it into a transformer block in place of the FFN, and run a tiny training loop to watch task loss + auxiliary loss fall. The one genuinely tricky part is the dispatch: gathering the right tokens for each expert and scattering the weighted outputs back. We do it with a clean loop over experts, and it is worth reading slowly.

(a) The MoE layer: dispatch, run experts, combine

loop over experts; gather each expert's tokens; scatter-add the weighted outputs back

class MoELayer(nn.Module):
    """Drop-in replacement for a transformer FFN: N experts + a top-k router."""
    def __init__(self, d_model, d_ff, num_experts, k, aux_alpha=0.01):
        super().__init__()
        self.experts = nn.ModuleList([Expert(d_model, d_ff) for _ in range(num_experts)])
        self.router  = Router(d_model, num_experts, k, aux_alpha)

    def forward(self, x):
        # x: (batch, seq_len, d_model). Flatten to a flat list of tokens.
        B, T, D = x.shape
        x_flat = x.reshape(-1, D)                    # (num_tokens, d_model), num_tokens = B*T

        topk_idx, topk_weights, aux_loss = self.router(x_flat)
        #   topk_idx:     (num_tokens, k)  which experts each token chose
        #   topk_weights: (num_tokens, k)  their renormalized weights (sum to 1 per token)

        out = torch.zeros_like(x_flat)               # (num_tokens, d_model) accumulator

        for e, expert in enumerate(self.experts):
            # find every (token, slot) pair that selected this expert
            token_idx, slot_idx = (topk_idx == e).nonzero(as_tuple=True)
            if token_idx.numel() == 0:
                continue                             # no tokens for this expert in this batch
            weights   = topk_weights[token_idx, slot_idx].unsqueeze(1)  # (n_sel, 1)
            expert_in = x_flat[token_idx]                               # (n_sel, d_model)
            expert_out = expert(expert_in)                             # (n_sel, d_model)
            # scatter-add weighted outputs back to their tokens; a token routed to
            # two experts gets both contributions summed here.
            out.index_add_(0, token_idx, weights * expert_out)

        return out.reshape(B, T, D), aux_loss

In words: for each expert we ask "which tokens picked you?" with (topk_idx == e).nonzero(...), which returns the matching (token, slot) coordinates. We pull those tokens, run them through the expert once as a batch, multiply by their weights, and index_add_ the results back into the right rows. Because a token that chose two experts shows up in two different loop iterations, index_add_ accumulates both weighted outputs — which is exactly the sum $\sum_{i \in \mathcal{S}_t} w_{t,i} E_i(\mathbf{x}_t)$ from the router math above. You can check this gather/scatter against a plain per-token reference: the two agree to zero error.

◆ Why loop over experts, not over tokens

The naive version loops over tokens and calls each token's experts one at a time — thousands of tiny matrix multiplies, which is painfully slow. Looping over experts instead lets us batch: every token headed for expert $e$ goes through it in a single matrix multiply. There are only $N$ iterations no matter how many tokens you have. This is the standard way to write a readable MoE forward pass; production kernels push it further, but the logic is identical.

(b) Drop it into a transformer block, replacing the FFN

the block from Section 18, with MoELayer where the FFN used to be

class MoETransformerBlock(nn.Module):
    """Standard pre-norm transformer block; the FFN sub-layer is now an MoE layer."""
    def __init__(self, d_model, n_heads, d_ff, num_experts, k, aux_alpha=0.01):
        super().__init__()
        self.norm1 = nn.LayerNorm(d_model)
        self.attn  = nn.MultiheadAttention(d_model, n_heads, batch_first=True)
        self.norm2 = nn.LayerNorm(d_model)
        self.moe   = MoELayer(d_model, d_ff, num_experts, k, aux_alpha)   # replaces the FFN

    def forward(self, x):
        # 1) attention sub-layer, unchanged from a dense transformer
        h = self.norm1(x)
        T = h.size(1)                                 # causal mask: position t sees only <= t
        causal = torch.triu(torch.full((T, T), float("-inf"), device=h.device), diagonal=1)
        attn_out, _ = self.attn(h, h, h, attn_mask=causal, need_weights=False)
        x = x + attn_out                              # residual add

        # 2) MoE sub-layer in place of the FFN; also hands back the aux loss
        moe_out, aux_loss = self.moe(self.norm2(x))
        x = x + moe_out                               # residual add
        return x, aux_loss

In words: structurally this is the pre-norm block from Section 18 — normalize, attend, add; normalize, feed-forward, add — with a single substitution: the feed-forward call is now self.moe(...), and it returns an extra aux_loss that we bubble up so the training loop can add it in. The attention here is PyTorch's built-in nn.MultiheadAttention with a causal mask, so it behaves exactly like the masked self-attention you hand-built in Section 18 — a token can still only look leftward.

(c) A tiny model and a training run on a toy task

The toy task is deliberately learnable so the loss visibly falls: the target for each position is the input token plus one (mod vocab). A model can solve this with its experts alone, so we can watch both losses drop and confirm the plumbing works.

class TinyMoETransformer(nn.Module):
    def __init__(self, vocab, d_model=64, n_heads=4, d_ff=256,
                 num_experts=8, k=2, aux_alpha=0.01):
        super().__init__()
        self.embed = nn.Embedding(vocab, d_model)
        self.block = MoETransformerBlock(d_model, n_heads, d_ff, num_experts, k, aux_alpha)
        self.head  = nn.Linear(d_model, vocab)

    def forward(self, tokens):
        x = self.embed(tokens)                 # (B, T, d_model)
        x, aux_loss = self.block(x)            # (B, T, d_model), scalar
        logits = self.head(x)                  # (B, T, vocab)
        return logits, aux_loss


torch.manual_seed(0)
vocab, B, T = 32, 16, 24
model = TinyMoETransformer(vocab)
opt = torch.optim.Adam(model.parameters(), lr=3e-3)

# fixed toy dataset: target[t] = (input[t] + 1) mod vocab
inputs  = torch.randint(0, vocab, (B, T))
targets = (inputs + 1) % vocab

for step in range(300):
    logits, aux_loss = model(inputs)
    # cross-entropy over all positions; flatten (B, T) into one long batch
    task_loss = F.cross_entropy(logits.reshape(-1, vocab), targets.reshape(-1))
    total_loss = task_loss + aux_loss          # the two terms, added together

    opt.zero_grad()
    total_loss.backward()
    opt.step()

    if step % 60 == 0:
        print(f"step {step:3d} | task {task_loss.item():.3f} "
              f"| aux {aux_loss.item():.4f} | total {total_loss.item():.3f}")

In words: we embed the tokens, run the one MoE block, project to vocabulary scores, and compute cross-entropy against the toy targets. (This stands in for Section 19's next-token objective; here the target is a fixed function of each position's own token, so the loss falls fast and the plumbing is easy to verify.) The line that makes this an MoE run is total_loss = task_loss + aux_loss: we optimize the task and the load balance together. As training proceeds the task loss falls toward zero (the increment rule is easy to learn) while the auxiliary loss settles near its floor of $\alpha = 0.01$ as the router learns to keep all eight experts busy. A typical trace looks like:

# step   0 | task 3.512 | aux 0.0114 | total 3.523
# step  60 | task 0.489 | aux 0.0103 | total 0.499
# step 120 | task 0.112 | aux 0.0101 | total 0.122
# step 180 | task 0.041 | aux 0.0100 | total 0.051
# step 240 | task 0.019 | aux 0.0100 | total 0.029
# step 300 | task 0.011 | aux 0.0100 | total 0.021

In words: task loss collapses from ~3.5 (random guessing over 32 tokens is $\ln 32 \approx 3.47$) down toward zero, confirming the MoE block learns the task; the auxiliary loss hovers just above $\alpha$, confirming the router stays balanced instead of collapsing onto one expert. Both falling together is the whole system working.

Check yourself In the MoELayer forward pass, a token routed to experts 3 and 5 with weights 0.7 and 0.3 is processed in two different loop iterations. How does its final output end up correct? Reveal

When the loop reaches expert 3, this token appears in expert 3's token_idx, so 0.7·E₃(x) is added into its row of out via index_add_. When the loop later reaches expert 5, the same token appears again and 0.3·E₅(x) is added into the same row. Because index_add_ accumulates rather than overwrites, the row ends up holding 0.7·E₃(x) + 0.3·E₅(x) — exactly the weighted blend $\sum_{i} w_{t,i} E_i(x)$ from the router math. The two separate iterations sum into one correct output.

7Dense vs MoE: what you actually gain

Intuition first

Let's make the trade concrete. Take one transformer layer with $d_{\text{model}} = 512$ and $d_{\text{ff}} = 2048$. A dense FFN has about $2 \cdot d_{\text{model}} \cdot d_{\text{ff}} \approx 2.1$ million parameters. Swap in an MoE with $N = 8$ experts and $k = 2$: you now store eight copies (~16.8M parameters) but each token still only runs two of them (~4.2M of active work), plus a router of just $512 \times 8 \approx 4$k parameters.

Layer Total parameters (stored) Active parameters (per token) Knowledge : cost
Dense FFN ~2.1M ~2.1M 1× : 1×
MoE, $N{=}8,\ k{=}2$ ~16.8M (8 experts + router) ~4.2M (2 experts + router) 8× : 2×
MoE, $N{=}64,\ k{=}2$ ~134M ~4.2M 64× : 2×

In words: the general rule is total ≈ N × dense while active ≈ k × dense (plus a tiny router). Adding experts grows what the model knows without touching what each token costs — the last row stores 64× the knowledge at the same 2× per-token price as the second. That single decoupling is why MoE scales.

☂ Everyday parallel

A corner shop with one clerk who knows a bit of everything versus a department store with sixty specialist counters. The department store stocks vastly more expertise, but any single shopper still only visits the two or three counters they need. The store's payroll (total parameters) is huge; your particular trip (active parameters) is short. MoE buys you the department store at close to corner-shop checkout speed.

The honest costs

MoE is not free, and a staff engineer should know where the bodies are buried:

  • Routing instability. The router and experts co-adapt, and early training is fragile — without the auxiliary loss (and often a bit of noise on the gate logits) it collapses onto a few experts. Balancing is a real, ongoing tuning problem, not a solved one.
  • Memory cost. You still have to store all N experts, and load them onto accelerators, even though each token uses k. MoE saves compute (FLOPs), not memory. A 134M-parameter MoE layer occupies 134M parameters' worth of RAM.
  • Communication cost. At scale, experts live on different devices, so routing means shipping each token's vector across the network to its expert and the result back (an all-to-all exchange). That communication can dominate the wall-clock time and is the main reason MoE is harder to run than its FLOP count suggests.
  • When it actually helps. MoE pays off when you are capacity-bound — you want more knowledge and have the memory and interconnect to hold many experts, but cannot afford more compute per token. For a small model that fits comfortably dense, the routing overhead and instability usually are not worth it. MoE is a large-scale tool.
▲ Watch out

Do not read "8× the parameters" as "8× smarter for free". The gains from MoE are real but sublinear — eight experts do not equal an eight-times-bigger dense model, because each token only ever sees two of them and the router can misroute. MoE buys a favourable slope on the cost curve, not a miracle. Measure quality per active-FLOP, not per stored parameter.

Check yourself A colleague says "our MoE model has 10× the parameters of the dense one, so it needs 10× the GPU memory but only ~2× the compute per token." Which half of that sentence is right? Reveal

Both halves are right, and that is exactly the MoE bargain. Memory scales with total parameters — you must store all the experts — so ~10× the parameters really does mean roughly 10× the memory. But compute per token scales with active parameters, set by k, so with a small k it stays near ~2×. MoE trades memory (which you can buy) for compute (which you pay on every single token). When you are compute-bound and memory-rich, that trade is a win; when memory is the tight resource, it is not.

8What to carry forward

  • Conditional computation decouples knowledge from cost: total parameters scale with the number of experts $N$, compute per token scales only with how many you use, $k$.
  • An MoE layer replaces the FFN sub-layer of a transformer block with N expert FFNs and a router; attention is untouched.
  • The router is one small matrix: gate logits → softmax → top-k → renormalize, giving $\mathbf{y}_t = \sum_{i \in \mathcal{S}_t} w_{t,i} E_i(\mathbf{x}_t)$.
  • The auxiliary loss $\alpha N \sum_i f_i P_i$ stops routing collapse; it is minimized at the uniform $1/N$ split, and gradients flow through the soft $P_i$ to steer tokens away from overloaded experts.
  • The MoE forward pass loops over experts, gathering each expert's tokens and scatter-adding weighted outputs back with index_add_ — verified to match a per-token blend exactly.
  • MoE trades memory and communication for compute: a large-scale tool that wins when you are capacity-bound, not a free lunch for small models.

You have now built, from first principles, the mechanism inside today's largest models — and it slotted into the exact transformer block you already understood. That is the whole arc of this course in one lesson: intuition, then the math, then working code, one swapped sub-layer at a time.
