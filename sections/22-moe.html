Mixture of Experts from Scratch

The technique behind several of today's largest models. Build the router, derive the balancing loss, and put it into the transformer you already understand.

70 min read
You'll learn
  • conditional computation
  • top-k router math
  • the load-balancing auxiliary loss (derived)
  • a full annotated MoE transformer, dense vs MoE

Every model you have built so far runs all of its weights on every input. A bigger model means more weights, and more weights mean more arithmetic per token. Cost and capacity are chained together. This lesson breaks that chain. A Mixture of Experts (MoE) lets you grow the number of parameters a model owns without growing the work it does per token. Some of today's largest open models use it. They store hundreds of billions of parameters but use only a few tens of billions for each token. We will derive the method and build a working one.

◆ The one idea to hold onto

A dense layer asks every parameter about every token. An MoE layer keeps many separate sub-networks (the experts), and a tiny router sends each token to only a few of them. Total knowledge goes up; work per token stays flat. This lesson is about building that router and stopping it from cheating.

This is the capstone. It uses the transformer block from Section 18 and the next-token training setup from Section 19. If those are fresh in your mind, this lesson will be easy to follow. An MoE changes only one sub-layer of the block you already know.

1Conditional computation: pay for what you use

Intuition first

Here is the tension. Bigger models usually perform better. This is one of the most reliable findings in machine learning. But in a normal (dense) network, “bigger” means every input runs through every weight. Doubling the parameters roughly doubles the compute (the arithmetic work) for every token, and that gets expensive fast. Conditional computation is the way out. Instead of running the whole network on each token, run only the part of the network that is relevant to that token. Most weights stay unused for most inputs.

☂ Everyday parallel

You walk into a large hospital with a broken wrist. You are not examined by all three hundred doctors on staff. The front desk (the router) looks at your problem and sends you to an orthopedist. The hospital's total expertise is huge: cardiology, neurology, pediatrics, and more. But your visit uses the time of only one or two specialists. The hospital can hire more specialists without making each visit longer. That is conditional computation: a lot of available skill, but each case uses only the relevant part.

Now the math

Let one expert sub-network cost $C$ units of compute to run on one token. Put $E$ of these experts side by side. Let the router send each token to $k$ of them, with $k \ll E$ (read “$k$ is much smaller than $E$”). Then:

$$ \text{Total parameters} \;\propto\; E\,C, \qquad \text{Compute per token} \;\propto\; k\,C $$

In words: the knowledge you store grows with the number of experts $E$. The work you do per token grows only with how many experts you use, $k$. With $E = 64$ experts and $k = 2$, you store $64\times$ the parameters of one expert but do only $2\times$ its work. In a dense model these two numbers are tied together. Here they are separate: $E$ sets the storage and $k$ sets the compute.

Definition

A model's active parameters are the weights that take part in processing a given token. Its total parameters are all the weights it stores. In a dense model these two numbers are equal. The promise of MoE is to make total parameters large while keeping active parameters small.

◆ Why this matters now

Several large models with published details use this design. Switch-C (2021) has about 1.6 trillion parameters. Mixtral 8x7B (2023) stores about 47 billion parameters but uses about 13 billion per token. DeepSeek-V3 (2024) stores 671 billion and uses 37 billion per token. In each case, the equation above is the reason. You are about to build the same mechanism at a small scale.

Check yourself An MoE layer has $E = 8$ experts, each the same size as a dense feed-forward block, and routes each token to $k = 2$ of them. Predict how many times more parameters it stores than one dense block, and how much more compute it does per token. Reveal

It stores 8× the parameters (eight full copies of the block), plus a tiny router. But it runs only 2 of those blocks on any token, so it does about 2× the compute per token, not 8×. That gap between 8× the knowledge and 2× the cost is the whole point. The router's own cost is very small: it is one small matrix, which we size next.

2Where the experts go: one swapped sub-layer

Intuition first

Recall the transformer block from Section 18. Each block has two sub-layers. The self-attention sub-layer is where tokens look at each other and mix information. The feed-forward network (FFN) is a small two-layer network applied to each token on its own. The FFN holds most of a transformer's parameters and does most of the per-token computation. MoE makes one change: replace that single FFN with a set of FFNs plus a router. Attention does not change.

So the block goes from this:

$$ \mathbf{x} \;\to\; \mathbf{x} + \text{Attention}(\mathbf{x}) \;\to\; \mathbf{x} + \text{FFN}(\mathbf{x}) $$

to this, with only the second step changed:

$$ \mathbf{x} \;\to\; \mathbf{x} + \text{Attention}(\mathbf{x}) \;\to\; \mathbf{x} + \text{MoE}(\mathbf{x}) $$

In words: the $+$ is the residual connection (add the sub-layer's output back onto its input, from Section 18). The only difference is that the fixed FFN is now an MoE block. Inside, it picks a few experts per token instead of running one shared network. From the outside, the block still takes a vector of size $d_{\text{model}}$ in and returns one of the same size.

Definition

An expert is an ordinary FFN, the same two-layer network the dense block used. Nothing inside an expert is special. The specialization comes from the router: it learns to send different kinds of tokens to different experts, so each expert can specialize. We build the expert first because you already know it.

The same thing in PyTorch

an expert is a plain feed-forward block

import torch
import torch.nn as nn
import torch.nn.functional as F

class Expert(nn.Module):
    """One expert = the standard transformer FFN: expand, nonlinearity, project back."""
    def __init__(self, d_model, d_ff):
        super().__init__()
        self.up   = nn.Linear(d_model, d_ff)   # widen d_model -> d_ff
        self.down = nn.Linear(d_ff, d_model)   # narrow d_ff  -> d_model

    def forward(self, x):
        # x: (num_tokens, d_model)  ->  (num_tokens, d_model)
        return self.down(F.gelu(self.up(x)))

In words: this is the FFN from a normal transformer. It has a wide hidden layer of size $d_{\text{ff}}$ (usually $4\,d_{\text{model}}$). Then comes a GELU nonlinearity (a smooth activation function; see Section 9). Last is a projection back to $d_{\text{model}}$. An MoE layer will hold $E$ of these in a list.

Check yourself What would go wrong if we routed tokens to separate experts inside the attention sub-layer instead of the FFN? Reveal

Attention exists so that tokens can mix with each other. If tokens were split among separate experts there, a token could no longer see tokens that went elsewhere, and those connections would break. The FFN treats each token independently: it maps one vector to one vector. So each token can go to its own expert without breaking anything. The FFN also holds most of the parameters and per-token compute, so it is the sub-layer worth making sparse.

3The router: top-k gating, derived

Intuition first

The router (also called the gating network) is the front desk. For each token it answers two questions. Which experts should handle this token? And how much should each of them count? It answers with a small learned matrix, a softmax, and a “keep only the top few” step. The router is one linear layer followed by a selection rule. Let's build it step by step.

Now the math

Take one token's vector $\mathbf{x}_t \in \mathbb{R}^{d}$. Here $d = d_{\text{model}}$, and $t$ indexes the token. The router owns one weight matrix $\mathbf{W}_g \in \mathbb{R}^{E \times d}$, where $E$ is the number of experts. Step 1: gate logits. Multiply to get one raw score per expert:

$$ \mathbf{g}_t \;=\; \mathbf{W}_g\,\mathbf{x}_t \;\in\; \mathbb{R}^{E} $$

In words: $\mathbf{g}_t$ is a list of $E$ numbers, one per expert. Each is the raw affinity of this token for that expert. These are called logits: raw scores, not yet probabilities. They can be negative and do not sum to anything in particular. The router matrix $\mathbf{W}_g$ is tiny. For $d = 512$ and $E = 8$ it has about four thousand numbers, which is very small next to one expert.

Step 2: routing probabilities. Turn the raw scores into probabilities with a softmax. (A softmax turns a list of numbers into positive values that sum to 1; see Section 4.)

$$ p_{t,i} \;=\; \operatorname{softmax}(\mathbf{g}_t)_i \;=\; \frac{\exp(g_{t,i})}{\sum_{j=1}^{E} \exp(g_{t,j})} $$

In words: $p_{t,i}$ is the probability the router gives to expert $i$ for token $t$. The exponential makes every score positive. Dividing by the sum makes the scores add up to 1. Now we have a clean distribution over experts for this token, for example $[0.6, 0.25, 0.1, 0.05]$.

Step 3: top-k selection. Running all $E$ experts would defeat the purpose. So we keep only the $k$ experts with the highest probabilities. We call that chosen set $\mathcal{S}_t$:

$$ \mathcal{S}_t \;=\; \operatorname*{top\text{-}k}_{\,i}\; p_{t,i} \quad\text{(the } k \text{ experts with the largest } p_{t,i}) $$

In words: $\mathcal{S}_t$ is the short list. For $k = 2$ it holds the two experts this token scored highest. Every expert outside $\mathcal{S}_t$ is switched off for this token and does no work. This selection step is where the “sparse” in “sparse MoE” comes from.

Step 4: renormalize the survivors. The kept probabilities no longer sum to 1, because we threw the rest away. If they summed to 0.85, we would scale this token's output down by 15% without meaning to. So we divide by their own sum:

$$ w_{t,i} \;=\; \frac{p_{t,i}}{\displaystyle\sum_{j \in \mathcal{S}_t} p_{t,j}} \qquad \text{for } i \in \mathcal{S}_t $$

In words: $w_{t,i}$ is the final weight for expert $i$ on token $t$. After this step the chosen weights sum to 1, so the experts' outputs are blended, not shrunk. If $k = 2$ and the top two probabilities are 0.6 and 0.25, the weights are $0.6 / 0.85 \approx 0.706$ and $0.25 / 0.85 \approx 0.294$.

Step 5: combine. Run the token through each chosen expert and add up the outputs, weighted by $w_{t,i}$:

$$ \mathbf{y}_t \;=\; \sum_{i \in \mathcal{S}_t} w_{t,i}\;\, \mathrm{FFN}_i(\mathbf{x}_t) $$

In words: $\mathrm{FFN}_i$ is expert $i$. The output $\mathbf{y}_t$ is a weighted average of the $k$ chosen experts' answers. Experts the router trusts more get a bigger say. This one line is the whole forward pass of an MoE layer. The rest of the code does it efficiently for a whole batch at once.

◆ Why the router can learn at all

The weights $w_{t,i}$ multiply the experts' outputs. So gradients (from backprop) flow back through them into $\mathbf{W}_g$. If giving more weight to expert 3 would lower the loss, the router is pushed to raise $p_{t,3}$. The hard “pick the top $k$” step has no gradient. But the kept experts are weighted by their soft probabilities, so the router still gets a gradient through them. That is why top-k gating trains end to end with plain gradient descent.

▲ Watch out

With $k = 1$, Step 4 always gives $w_{t,i} = p/p = 1$. The weight is then a constant, so the task loss sends no gradient to the router. For this reason Switch Transformer (which uses $k = 1$) skips the renormalization and uses the raw probability $p_{t,i}$ as the weight. Renormalize only when $k \ge 2$.

The same thing in PyTorch

router: linear, softmax, top-k, renormalize (the aux loss is derived next)

class Router(nn.Module):
    """Scores each token over E experts, keeps the top-k, and renormalizes their weights."""
    def __init__(self, d_model, num_experts, k, aux_weight=0.01):
        super().__init__()
        self.gate = nn.Linear(d_model, num_experts, bias=False)  # W_g: shape (E, d_model)
        self.num_experts = num_experts
        self.k = k
        self.aux_weight = aux_weight                             # lambda_aux

    def forward(self, x):
        # x: (num_tokens, d_model)
        logits = self.gate(x)                      # (num_tokens, E)  gate logits g
        probs  = logits.softmax(dim=-1)            # (num_tokens, E)  routing probs p

        # top-k experts per token
        topk_probs, topk_idx = probs.topk(self.k, dim=-1)   # each (num_tokens, k)
        # renormalize the survivors so their weights sum to 1
        topk_weights = topk_probs / topk_probs.sum(dim=-1, keepdim=True)

        aux_loss = self._load_balancing_loss(probs, topk_idx)  # derived in section 4
        return topk_idx, topk_weights, aux_loss

In words: the four math steps map onto four lines. topk returns both the kept probabilities and the indices of their experts. Dividing by topk_probs.sum(...) is the renormalize step. The _load_balancing_loss method comes in the next section, where we derive what it computes.

Check yourself A token's softmax over 4 experts is $[0.5, 0.3, 0.15, 0.05]$ and $k = 2$. Predict which experts are chosen and their final weights. Reveal

The top two are 0.5 (expert 0) and 0.3 (expert 1), so $\mathcal{S} = \{0, 1\}$. Their sum is 0.8, so the weights are $0.5 / 0.8 = 0.625$ and $0.3 / 0.8 = 0.375$. Experts 2 and 3 are switched off for this token. The weights sum to 1, so the output is a real blend, $0.625\,\mathrm{FFN}_0 + 0.375\,\mathrm{FFN}_1$, not a faded version.

Check yourself Find the bug: someone sets k=1 in the Router above to get a Switch-style layer. The task loss falls a little, but the routing never seems to improve. Why? Reveal

With k=1, topk_probs / topk_probs.sum(...) is always 1. The weight no longer depends on the router, so the task loss gives the router no gradient. Only the auxiliary loss still moves it. The fix is to use the raw topk_probs as the weights when k == 1.

4Load balancing: deriving the auxiliary loss

Intuition first

Left alone, the router cheats. Early in training, one expert happens to be slightly better. So the router sends it slightly more tokens. So it trains faster and gets even better. So the router sends it even more tokens. This is a rich-get-richer feedback loop, also called routing collapse. A few experts get almost all the tokens, and the rest never get enough tokens to learn. You paid for $E$ experts and got 2. We need a gentle force that keeps the traffic spread out.

☂ Everyday parallel

Back at the hospital, one doctor gets a great reputation. Everyone asks for that doctor, so the queue grows to three hours while four other good doctors sit in empty rooms. The hospital is underused, and the famous doctor is overloaded. The fix is a scheduling rule that nudges patients toward the idle doctors. It does not force anyone; it tilts the odds so the whole staff stays busy. The auxiliary loss is that scheduling rule, written as math and added to training.

Definition

An auxiliary loss is an extra term added to the training loss. It does not measure task performance. Instead, it pushes some internal quantity toward a shape we want. Here it pushes the token traffic toward an even spread across experts. The model minimizes task loss + auxiliary loss together.

Now the math

We want to measure imbalance and then penalize it. Let $T$ be the number of tokens in the batch (all sequences flattened into one list). Each token fills $k$ routing slots, so there are $kT$ slots in total. For each expert $i$ we define two quantities. The first is a hard count of what was routed:

$$ f_i \;=\; \frac{1}{kT} \sum_{t=1}^{T} \mathbb{1}\big[\, i \in \mathcal{S}_t \,\big] $$

In words: $f_i$ is the share of routing slots that went to expert $i$. The symbol $\mathbb{1}[\cdot]$ is the indicator: it is 1 when the condition inside is true and 0 otherwise. We count how many tokens have expert $i$ in their top $k$ and divide by the number of slots, $kT$. Because every slot goes to some expert, $\sum_i f_i = 1$. A token can use an expert at most once, so no $f_i$ can be larger than $1/k$.

The second is a soft average: how much probability the router wanted to give each expert, before the hard cutoff:

$$ P_i \;=\; \frac{1}{T} \sum_{t=1}^{T} p_{t,i} $$

In words: $P_i$ is the mean router probability for expert $i$, averaged over all tokens. It uses the full softmax $p_{t,i}$, not only the chosen experts. Each token's probabilities sum to 1, so $\sum_i P_i = 1$ too. $P_i$ is smooth and differentiable, which will matter soon. Think of $f_i$ as “who was sent” and $P_i$ as “who the router leaned toward, on average”.

The Switch Transformer auxiliary loss multiplies these two, sums over the experts, and scales the result:

$$ L_{\text{aux}} \;=\; \lambda_{\text{aux}} \, E \sum_{i=1}^{E} f_i \, P_i $$

In words: $\lambda_{\text{aux}}$ is a small weight, typically 0.01. $E$ is the number of experts. It is there so the loss keeps the same size when you add experts. The core is $\sum_i f_i P_i$: a dot product between the hard load and the soft preference. At perfect balance, $f_i = P_i = 1/E$, so the sum is $E \cdot (1/E)^2 = 1/E$ and $L_{\text{aux}} = \lambda_{\text{aux}}$. (Switch Transformer uses $k = 1$, where our $f_i$ is the same as theirs. Dividing by $k$ keeps the balanced value at $\lambda_{\text{aux}}$ for any $k$.)

Why this loss spreads the load

Start with the gradient. The count $f_i$ comes from a hard top-k choice, so it has no gradient. Training treats it as a fixed number. Only $P_i$ carries a gradient:

$$ \frac{\partial L_{\text{aux}}}{\partial P_i} \;=\; \lambda_{\text{aux}}\, E\, f_i $$

In words: the push on expert $i$'s probability is proportional to its current load $f_i$. Gradient descent lowers every $P_i$, but it lowers the overloaded ones (large $f_i$) the most. Since probabilities must sum to 1, the idle experts gain probability. Top-k picks the experts with the highest probabilities, so the next batch sends more tokens to the idle experts.

Where does this stop? Top-k sends tokens where the probabilities are high, so over training $f_i$ and $P_i$ rise and fall together. Look at the case $f_i = P_i$ for all $i$. The loss then depends on $\sum_i P_i^2$, and the Cauchy–Schwarz inequality gives its smallest value:

$$ \Big(\sum_{i=1}^{E} P_i \cdot 1\Big)^{2} \;\le\; \Big(\sum_{i=1}^{E} P_i^{2}\Big)\Big(\sum_{i=1}^{E} 1^{2}\Big) \;\;\Longrightarrow\;\; 1 \;\le\; E \sum_{i=1}^{E} P_i^{2} $$ $$ \sum_{i=1}^{E} P_i^{2} \;\ge\; \frac{1}{E}, \qquad \text{with equality only if } P_i = \tfrac{1}{E}\ \text{for all } i $$

In words: when load and preference agree, the sum of squares is smallest when every expert has the same share, $1/E$. A lopsided distribution (one expert at 0.9) has a big sum of squares. A flat one has the smallest. So, together with the gradient above, the loss pushes routing toward the even $1/E$ split. Note that this is not a proof that $\sum_i f_i P_i$ is smallest at balance for every pair $f$, $P$. When $f$ and $P$ disagree, the sum can be lower. But top-k keeps them close, and the gradient always pushes toward balance.

The weight $\lambda_{\text{aux}}$ is a real trade-off. If it is too small, the balancing force is too weak to stop collapse, and training drifts back to a few favorite experts. If it is too large, it overpowers the task loss. The router is then forced to spread tokens evenly even when that hurts the prediction. The common value $\lambda_{\text{aux}} = 0.01$ keeps balance without drowning out the task.

The same thing in PyTorch

the load-balancing loss (a method of Router)

    def _load_balancing_loss(self, probs, topk_idx):
        # probs:    (num_tokens, E)  full softmax routing probabilities
        # topk_idx: (num_tokens, k)  indices of the experts each token selected
        mask = torch.zeros_like(probs)
        mask.scatter_(1, topk_idx, 1.0)           # mask[t, i] = 1 if token t chose expert i

        f = mask.mean(dim=0) / self.k             # (E,)  share of routing slots per expert; sums to 1
        P = probs.mean(dim=0)                     # (E,)  mean router probability per expert
        self.last_load = f.detach()               # kept only so we can print it later
        return self.aux_weight * self.num_experts * (f * P).sum()

In words: scatter_ writes a 1 into the mask at each chosen (token, expert) position. Averaging that mask over tokens and dividing by $k$ gives $f_i$. Averaging the probabilities gives $P_i$. The last line is $\lambda_{\text{aux}} E \sum_i f_i P_i$. The result is one number that we add to the task loss. This method belongs inside the Router class, which is why it is indented.

▲ Watch out

Do not detach the P = probs.mean(0) line or wrap it in torch.no_grad(). The gradient must flow through $P_i$ back into the router. It is fine that $f_i$ (built from the hard topk_idx) has no gradient; that is by design. If you block the gradient on $P_i$, the auxiliary loss becomes a constant. It then does nothing, and your experts can collapse without any warning.

Check yourself A router with $E = 4$ experts and $k = 1$ collapses to $f = [1, 0, 0, 0]$ and $P = [0.97, 0.01, 0.01, 0.01]$. Predict $L_{\text{aux}}$ as a multiple of $\lambda_{\text{aux}}$, and compare it with a balanced router. Reveal

Collapsed: $\sum_i f_i P_i = 1 \cdot 0.97 = 0.97$, so $L_{\text{aux}} = \lambda_{\text{aux}} \cdot 4 \cdot 0.97 \approx 3.9\,\lambda_{\text{aux}}$. Balanced, with $f = P = [0.25, 0.25, 0.25, 0.25]$: the sum is $4 \cdot 0.25^2 = 0.25$, so $L_{\text{aux}} = \lambda_{\text{aux}}$. The collapsed router pays almost four times more. The gradient $\lambda_{\text{aux}} E f_i$ is also largest for expert 0 ($f_0 = 1$), so gradient descent pushes its probability down hardest.

Check yourself In Figure 22.2 (bottom), expert 1 has $P_1 = 0.82$ but $f_1$ stops at exactly 0.5. Why can $f_1$ not go higher with $k = 2$? Reveal

Each token fills two slots and can use a given expert only once. Even if every token picks expert 1, it gets one slot out of two, so $f_1 = T / (2T) = 0.5 = 1/k$. The other slot must go to some other expert.

5Capacity factor and token dropping

Intuition first

On real hardware, experts run in parallel, and accelerators work best on fixed-size blocks of work. But routing changes from batch to batch. Sometimes one expert gets far more than its fair share. To keep the work a fixed size, each expert gets a capacity: the largest number of tokens it will accept in this batch. Tokens beyond that limit are dropped. The expert skips them, and they pass through the layer unchanged on the residual connection. They are not retried later.

Now the math

A capacity factor $c$ sets the per-expert budget. It is a small multiplier, usually between 1.0 and 2.0:

$$ \text{capacity} \;=\; c \cdot \frac{T \cdot k}{E} $$

In words: $T k / E$ is the number of tokens each expert would get if the $T$ tokens (each sent to $k$ experts) were split perfectly evenly. The factor $c$ adds slack: $c = 1.25$ means “accept up to 25% more than the fair share before dropping”. A bigger $c$ drops fewer tokens but wastes more compute on half-empty expert buffers. A smaller $c$ is cheaper but drops more. The load-balancing loss keeps the traffic even enough that few tokens get dropped.

To keep the code in this lesson clear, our implementation does not impose a capacity limit. It processes every token, so you can see the routing logic without the bookkeeping. In production systems, capacity matters a lot for speed. A well-balanced router rarely overflows, so the number of dropped tokens stays small.

▲ Watch out

Dropped tokens reduce quality without any error message. Suppose your capacity factor is too low and your router is imbalanced. Then many tokens skip the expert layer and get only the residual. For them, the FFN is switched off. If MoE quality is poor for no clear reason, measure the drop rate before you blame the experts.

Check yourself A batch has $T = 1024$ tokens, $E = 8$ experts, $k = 2$, and $c = 1.25$. Predict each expert's capacity. If a collapsed router sends half of all slots to one expert, how many of that expert's tokens are dropped? Reveal

Capacity is $1.25 \cdot 1024 \cdot 2 / 8 = 320$ tokens. Half of the $2 \cdot 1024 = 2048$ slots is 1024 tokens for that expert, so $1024 - 320 = 704$ of them are dropped. Those tokens get no FFN at all in this layer. This is why balance matters even more once there is a capacity limit.

6The full MoE layer, in a transformer, training

Intuition first

We have the Expert and the Router with its auxiliary loss. Now we assemble the MoELayer. It sends each token to its chosen experts and blends the results. Then we put it into a transformer block in place of the FFN. Finally, a tiny training loop lets us watch task loss + auxiliary loss fall. The one tricky part is the dispatch: collecting the right tokens for each expert and adding the weighted outputs back. We do it with a clear loop over experts. Read it slowly.

The same thing in PyTorch

the MoE layer: loop over experts, gather each expert's tokens, add the weighted outputs back

class MoELayer(nn.Module):
    """Drop-in replacement for a transformer FFN: E experts + a top-k router."""
    def __init__(self, d_model, d_ff, num_experts, k, aux_weight=0.01):
        super().__init__()
        self.experts = nn.ModuleList([Expert(d_model, d_ff) for _ in range(num_experts)])
        self.router  = Router(d_model, num_experts, k, aux_weight)

    def forward(self, x):
        # x: (batch, seq_len, d_model). Flatten to one list of tokens.
        batch, seq_len, d_model = x.shape
        x_flat = x.reshape(-1, d_model)              # (num_tokens, d_model)

        topk_idx, topk_weights, aux_loss = self.router(x_flat)
        #   topk_idx:     (num_tokens, k)  which experts each token chose
        #   topk_weights: (num_tokens, k)  their renormalized weights (sum to 1 per token)

        out = torch.zeros_like(x_flat)               # (num_tokens, d_model) accumulator

        for e, expert in enumerate(self.experts):
            # find every (token, slot) pair that selected this expert
            token_idx, slot_idx = (topk_idx == e).nonzero(as_tuple=True)
            if token_idx.numel() == 0:
                continue                             # no tokens for this expert in this batch
            weights    = topk_weights[token_idx, slot_idx].unsqueeze(1)  # (n_sel, 1)
            expert_in  = x_flat[token_idx]                               # (n_sel, d_model)
            expert_out = expert(expert_in)                               # (n_sel, d_model)
            # add the weighted outputs back into their tokens' rows; a token routed
            # to two experts gets both contributions summed here.
            out.index_add_(0, token_idx, weights * expert_out)

        return out.reshape(batch, seq_len, d_model), aux_loss

In words: for each expert we ask “which tokens picked you?” with (topk_idx == e).nonzero(...). It returns the matching (token, slot) positions. We take those tokens, run them through the expert once as a batch, and multiply by their weights. Then index_add_ adds the results into the right rows. A token that chose two experts appears in two loop iterations, and index_add_ adds both weighted outputs. That is the sum $\sum_{i \in \mathcal{S}_t} w_{t,i}\, \mathrm{FFN}_i(\mathbf{x}_t)$ from the router math.

Do not trust that claim; test it. The slow version below follows the formula one token at a time. It continues the snippets above.

def moe_reference(layer, x):
    """Slow per-token version of the MoE formula, for checking."""
    x_flat = x.reshape(-1, x.shape[-1])
    topk_idx, topk_weights, _ = layer.router(x_flat)
    rows = []
    for t in range(x_flat.shape[0]):             # one token at a time
        y = torch.zeros(x_flat.shape[1])
        for slot in range(topk_idx.shape[1]):    # its k chosen experts
            e = topk_idx[t, slot].item()
            y = y + topk_weights[t, slot] * layer.experts[e](x_flat[t])
        rows.append(y)
    return torch.stack(rows).reshape(x.shape)

torch.manual_seed(0)
layer = MoELayer(d_model=16, d_ff=64, num_experts=8, k=2)
x = torch.randn(2, 5, 16)
with torch.no_grad():
    fast, _ = layer(x)
    slow = moe_reference(layer, x)
print(torch.allclose(fast, slow, atol=1e-6))   # True
print(f"{(fast - slow).abs().max().item():.1e}")   # largest gap: float rounding only

In words: the two versions agree to about $10^{-7}$. The gap is not zero because the batched version adds the same numbers in a different order, and floating-point addition rounds differently. A gap this size means the logic is the same. A real bug (a wrong weight, a missed token) would give a gap near the size of the outputs themselves.

◆ Why loop over experts, not over tokens

The slow version loops over tokens and runs each token's experts one at a time. That is thousands of tiny matrix multiplies, which is very slow. Looping over experts lets us batch: every token sent to expert $e$ goes through it in one matrix multiply. There are only $E$ iterations, however many tokens you have. This is a standard way to write a readable MoE forward pass. Production kernels go further, but the logic is the same.

Next, we put the layer into a transformer block in place of the FFN.

the block from Section 18, with MoELayer where the FFN used to be

class MoETransformerBlock(nn.Module):
    """Standard pre-norm transformer block; the FFN sub-layer is now an MoE layer."""
    def __init__(self, d_model, n_heads, d_ff, num_experts, k, aux_weight=0.01):
        super().__init__()
        self.norm1 = nn.LayerNorm(d_model)
        self.attn  = nn.MultiheadAttention(d_model, n_heads, batch_first=True)
        self.norm2 = nn.LayerNorm(d_model)
        self.moe   = MoELayer(d_model, d_ff, num_experts, k, aux_weight)   # replaces the FFN

    def forward(self, x):
        # 1) attention sub-layer, unchanged from a dense transformer
        h = self.norm1(x)
        seq_len = h.size(1)                           # causal mask: position t sees only <= t
        causal = torch.triu(torch.full((seq_len, seq_len), float("-inf"), device=h.device), diagonal=1)
        attn_out, _ = self.attn(h, h, h, attn_mask=causal, need_weights=False)
        x = x + attn_out                              # residual add

        # 2) MoE sub-layer in place of the FFN; also hands back the aux loss
        moe_out, aux_loss = self.moe(self.norm2(x))
        x = x + moe_out                               # residual add
        return x, aux_loss

In words: this is the pre-norm block from Section 18: normalize, attend, add; normalize, feed-forward, add. There is one substitution. The feed-forward call is now self.moe(...), and it returns an extra aux_loss that we pass up so the training loop can add it. The attention is PyTorch's built-in nn.MultiheadAttention with a causal mask. It behaves like the masked self-attention from Section 19: a token can only look at itself and earlier tokens.

Finally, a tiny model and a training run. The toy task is easy on purpose, so the loss falls quickly. The target at each position is the input token plus one (mod the vocabulary size). The model can solve it without looking at other tokens, so we can check that the plumbing works.

a tiny MoE transformer trained on a toy task

class TinyMoETransformer(nn.Module):
    def __init__(self, vocab, d_model=64, n_heads=4, d_ff=256,
                 num_experts=8, k=2, aux_weight=0.01):
        super().__init__()
        self.embed = nn.Embedding(vocab, d_model)
        self.block = MoETransformerBlock(d_model, n_heads, d_ff, num_experts, k, aux_weight)
        self.head  = nn.Linear(d_model, vocab)

    def forward(self, tokens):
        x = self.embed(tokens)                 # (batch, seq_len, d_model)
        x, aux_loss = self.block(x)            # (batch, seq_len, d_model), scalar
        logits = self.head(x)                  # (batch, seq_len, vocab)
        return logits, aux_loss


torch.manual_seed(0)
vocab, batch, seq_len = 32, 16, 24
model = TinyMoETransformer(vocab)
opt = torch.optim.Adam(model.parameters(), lr=1e-3)

# fixed toy dataset: target[t] = (input[t] + 1) mod vocab
inputs  = torch.randint(0, vocab, (batch, seq_len))
targets = (inputs + 1) % vocab

for step in range(61):
    logits, aux_loss = model(inputs)
    # cross-entropy over all positions; flatten (batch, seq_len) into one long batch
    task_loss = F.cross_entropy(logits.reshape(-1, vocab), targets.reshape(-1))
    total_loss = task_loss + aux_loss          # the two terms, added together

    opt.zero_grad()
    total_loss.backward()
    opt.step()

    if step % 10 == 0:
        print(f"step {step:3d} | task {task_loss.item():.3f} "
              f"| aux {aux_loss.item():.4f} | total {total_loss.item():.3f}")

print("load per expert:", [round(v, 3) for v in model.block.moe.router.last_load.tolist()])

In words: we embed the tokens, run the one MoE block, project to vocabulary scores, and compute cross-entropy against the toy targets. This stands in for the next-token objective of Section 19. The line that makes this an MoE run is total_loss = task_loss + aux_loss: we optimize the task and the load balance together. Check yourself In the MoELayer forward pass, a token routed to experts 3 and 5 with weights 0.7 and 0.3 is processed in two different loop iterations. What would go wrong if the code used out[token_idx] = weights * expert_out instead of index_add_? Reveal

Plain assignment overwrites. When the loop reaches expert 3, the row gets $0.7\,\mathrm{FFN}_3(\mathbf{x})$. Later the loop reaches expert 5. Assignment then replaces the row with $0.3\,\mathrm{FFN}_5(\mathbf{x})$. Expert 3's part is lost. index_add_ adds instead, so the row ends up holding $0.7\,\mathrm{FFN}_3 + 0.3\,\mathrm{FFN}_5$, the weighted blend from the router math. The check against moe_reference would catch this bug: the gap would be large.

7Dense vs MoE: what you gain

Intuition first

Let's make the trade concrete. Take one transformer layer with $d_{\text{model}} = 512$ and $d_{\text{ff}} = 2048$. A dense FFN has about $2 \cdot d_{\text{model}} \cdot d_{\text{ff}} \approx 2.1$ million parameters. Now swap in an MoE with $E = 8$ experts and $k = 2$. You store eight copies (about 16.8M parameters). But each token runs only two of them (about 4.2M parameters of work), plus a router of $512 \times 8 \approx 4$k parameters.

Layer Total parameters (stored) Active parameters (per token) Knowledge : cost
Dense FFN ~2.1M ~2.1M 1× : 1×
MoE, $E{=}8,\ k{=}2$ ~16.8M (8 experts + router) ~4.2M (2 experts + router) 8× : 2×
MoE, $E{=}64,\ k{=}2$ ~134M ~4.2M 64× : 2×

In words: the general rule is total $\approx E \times$ dense and active $\approx k \times$ dense, plus a tiny router. Adding experts grows what the model stores without changing what each token costs. The last row stores 64× the parameters at the same 2× cost per token as the second row. This separation is why MoE scales.

The costs

MoE is not free. An engineer should know where the problems are:

  • Routing instability. The router and the experts adapt to each other, and early training is fragile. Without the auxiliary loss (and often some noise on the gate logits), routing can collapse onto a few experts. Balancing is still an active research and tuning problem.
  • Memory cost. You still have to store all $E$ experts and load them onto accelerators, even though each token uses $k$. MoE saves compute (FLOPs, floating-point operations), not memory. A 134M-parameter MoE layer needs memory for 134M parameters.
  • Communication cost. At scale, experts live on different devices. Routing then means sending each token's vector across the network to its expert and sending the result back (an all-to-all exchange). This communication can take most of the wall-clock time. It is the main reason MoE is harder to run than its FLOP count suggests.
  • When it helps. MoE pays off when you want more stored knowledge, have the memory and network to hold many experts, but cannot afford more compute per token. For a small model that fits easily as a dense model, the routing overhead and instability are usually not worth it. MoE is a tool for large scale.
▲ Watch out

Do not read “8× the parameters” as “8× smarter for free”. The gains from MoE are real but smaller than the parameter count suggests. Eight experts are not equal to an eight-times-bigger dense model. Each token sees only two of them, and the router can send a token to the wrong expert. MoE gives a better cost curve, not a miracle. Compare quality per active FLOP, not per stored parameter.

◆ Since Switch: what changed

The layer you built is the 2021-era design. Newer MoE models change a few parts:

  • Router z-loss (ST-MoE, Zoph et al., 2022). A second small auxiliary loss penalizes large gate logits. This keeps the softmax numerically stable and made training much less likely to diverge.
  • Fine-grained and shared experts (DeepSeekMoE, 2024). Split each expert into several smaller ones and route each token to more of them, so experts can specialize more narrowly. Add one or more shared experts that every token uses, to hold common knowledge. DeepSeek-V3 has 1 shared and 256 routed experts per MoE layer, with 8 routed experts active per token.
  • Balancing without an auxiliary loss (DeepSeek-V3, 2024). Each expert gets a bias that is added to its score only when choosing the top $k$. After each step, the bias goes up for underloaded experts and down for overloaded ones. The task loss is then not disturbed by a balancing gradient. (DeepSeek-V3 still keeps a very small auxiliary loss as a safety net.)

For scale: Switch-C has about 1.6 trillion parameters and 2048 experts per MoE layer with $k = 1$. Mixtral 8x7B has 8 experts with $k = 2$, about 47B total and 13B active parameters. DeepSeek-V3 has 671B total and 37B active parameters.

Check yourself A colleague says: “Our MoE model has 10× the parameters of the dense one, so it needs 10× the GPU memory but only about 2× the compute per token.” Judge each half of that claim. Reveal

Both halves can be right, and that is the MoE bargain. Memory grows with total parameters, because you must store all the experts. So about 10× the parameters means about 10× the memory for the weights. Compute per token grows with active parameters, set by $k$, so with $k = 2$ it stays near 2×. MoE trades memory for compute. When you are limited by compute and have memory to spare, that trade is a win. When memory is the tight resource, it is not.

8What to carry forward

  • Conditional computation separates knowledge from cost: total parameters grow with the number of experts $E$, compute per token only with how many you use, $k$.
  • An MoE layer replaces the FFN sub-layer of a transformer block with $E$ expert FFNs and a router. Attention does not change.
  • The router is one small matrix: gate logits, softmax, top-k, renormalize. The output is $\mathbf{y}_t = \sum_{i \in \mathcal{S}_t} w_{t,i}\,\mathrm{FFN}_i(\mathbf{x}_t)$.
  • The auxiliary loss $\lambda_{\text{aux}} E \sum_i f_i P_i$ fights routing collapse. Its value at perfect balance is $\lambda_{\text{aux}}$. Its gradient $\lambda_{\text{aux}} E f_i$ flows through the soft $P_i$ and pushes hardest on overloaded experts.
  • The MoE forward pass loops over experts, gathers each expert's tokens, and adds the weighted outputs back with index_add_. We checked it against a slow per-token version: they agree to float rounding.
  • MoE trades memory and communication for compute. It is a tool for large scale, not a free gain for small models.
