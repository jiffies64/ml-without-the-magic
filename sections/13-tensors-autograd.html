Tensors & Autograd

Everything you hand-derived in Section 10 — the graph, the chain rule, the backward pass — is about to be built and run for you automatically. You'll re-derive a small graph by hand, then watch autograd reproduce your gradients to the decimal.

26 min read
You'll learn

A tensor is PyTorch's one and only data structure — every input, weight, and output you will ever touch is one. Underneath it's refreshingly boring: a grid of numbers with a shape. What makes it interesting is that PyTorch can quietly track every operation you do to a tensor and, on request, hand you back the exact gradient — the thing you spent Section 10 computing by hand.

◆ The one idea to hold onto

A tensor is just an n-dimensional array. Autograd is the part of PyTorch that, as you do arithmetic on tensors, silently builds the same kind of computation graph you drew by hand in Section 10 — then runs the same backward pass to fill in every gradient, automatically.

1Tensors: arrays that can grow another dimension

Intuition first

A tensor is a number, or a list of numbers, or a grid of numbers, or a stack of grids of numbers — the same idea, just allowed to keep growing dimensions. A single number is a scalar (rank 0). A list is a vector (rank 1, one you already know from Section 1). A grid is a matrix (rank 2). A stack of matrices is a rank-3 tensor, and so on — PyTorch doesn't care where you stop.

☂ Everyday parallel

Think of a spreadsheet. One cell is a scalar. One row is a vector. The whole sheet is a matrix. Now imagine a workbook — several sheets stacked behind each other, all the same shape. That stack is a cube, a rank-3 tensor. Nothing new happened, you just kept stacking the same kind of thing one level deeper. That's all a tensor ever is.

Now the math

Every tensor carries three pieces of information you should check whenever something breaks:

  • shape — how many entries along each dimension, e.g. (64, 3, 28, 28) for 64 color images of 28×28 pixels.
  • dtype — what kind of number is stored (float32, int64, ...). Mixing dtypes in one operation is a common source of errors.
  • device — where the numbers physically live: the CPU's memory, or a GPU's memory. We'll come back to this at the end.

The same thing in PyTorch

making tensors and reading their shape

import torch

scalar = torch.tensor(3.0)                     # rank 0
vector = torch.tensor([1.0, 2.0, 3.0])          # rank 1, shape (3,)
matrix = torch.tensor([[1.0, 2.0],
                       [3.0, 4.0]])             # rank 2, shape (2, 2)
cube   = torch.zeros(2, 3, 4)                   # rank 3, shape (2, 3, 4)

print(vector.shape, vector.dtype, vector.device)
# torch.Size([3]) torch.float32 cpu
Check yourself A batch of 32 grayscale images, each 28×28 pixels. What rank is the tensor, and what's a reasonable shape? Reveal

Rank 3, shape (32, 28, 28) — one dimension for "which image in the batch" (32), and two for the pixel grid (28, 28). If the images were color you'd add a channel dimension, giving rank 4: (32, 3, 28, 28).

2Broadcasting: stretching a small tensor to fit a big one

Intuition first

Broadcasting is the rule PyTorch uses to let you combine tensors of different shapes without writing a loop. If one tensor is smaller along some dimension, PyTorch mentally "repeats" it along that dimension until the shapes match, then does the operation. No memory is actually copied — it just behaves as if it were.

☂ Everyday parallel

A spreadsheet of sale amounts, one row per transaction, and you want to apply a single 8% tax rate to every row. You don't write the rate 10,000 times — you write it once and the spreadsheet applies it to every row for you. Broadcasting is exactly that: one small tensor (the tax rate) automatically applied across every row of a bigger one (the transactions).

Now the math

PyTorch compares two shapes from the right-hand side, dimension by dimension. Two dimensions are compatible if they are equal, or if one of them is 1 (a size-1 dimension gets stretched to match). If every pair is compatible, the shapes broadcast together:

$$ (4, 3) \quad \text{and} \quad (3,) \;\longrightarrow\; \text{compatible: } (3,) \text{ acts like } (4, 3) $$

In words: a matrix with 4 rows and 3 columns, combined with a plain vector of length 3, works because the vector's single dimension (3) matches the matrix's last dimension (3). PyTorch treats the vector as if it were copied into all 4 rows.

The same thing in PyTorch

applying one row to every row — the tax-rate example

import torch

sales = torch.tensor([[100.0, 200.0, 300.0],   # 4 transactions,
                      [ 50.0,  75.0,  10.0],   # 3 line items each
                      [400.0, 100.0,  20.0],
                      [ 10.0,  10.0,  10.0]])  # shape (4, 3)

tax_rate = torch.tensor([0.08, 0.08, 0.08])    # shape (3,) — or just 0.08, a scalar

print(sales * tax_rate)   # shape (4, 3): the rate applied to every row, no loop
▲ The bug you will hit first

RuntimeError: The size of tensor a (3) must match the size of tensor b (4) at non-singleton dimension 1. Broadcasting only stretches dimensions that are exactly size 1 — it will never silently guess how to match a 3 against a 4. Print both .shapes and check which dimension refuses to line up.

Check yourself You have x of shape (64, 10) (a batch of 64 rows of 10 scores) and b of shape (10,) (a bias per column). Does x + b broadcast, and if so, to what shape? Reveal

Yes. Comparing from the right: 10 vs 10 match, and the leftover dimension on x (64) simply stays. The result has shape (64, 10) — the same bias vector added to every one of the 64 rows. This is exactly how a linear layer's bias term $\mathbf{Wx}+\mathbf{b}$ gets applied to a whole batch at once.

3Autograd: the payoff of Section 10

Intuition first

In Section 10 you built a computation graph by hand — nodes for each operation, arrows for how values flow forward, then walked the arrows backward applying the chain rule to get every gradient. Autograd is PyTorch doing exactly that same bookkeeping for you. Every time you do arithmetic on a tensor that has requires_grad=True, PyTorch records the operation as a node in a graph. Call .backward() and it walks that graph backward, the same direction you walked by hand, filling in .grad on every leaf.

☂ Everyday parallel

Doing your own taxes by hand once teaches you exactly how each deduction moves the final number. Tax software then does the identical arithmetic for you every year after — same rules, same order of operations, just automated. Section 10 was doing your taxes by hand. Autograd is the software. It isn't a different, cleverer method — it's the same method, run for you.

Definition

A tensor with requires_grad=True tells PyTorch "track every operation done to me, because I'll want a gradient with respect to this value later." Calling .backward() on a final scalar output triggers the backward pass; the result for each tracked tensor lands in its .grad attribute.

The same thing in PyTorch

the minimum working example

import torch

x = torch.tensor(3.0, requires_grad=True)
y = x ** 2 + 2 * x            # y = x^2 + 2x

y.backward()                  # walk the graph backward from y
print(x.grad)                 # tensor(8.)  because dy/dx = 2x + 2 = 2(3)+2 = 8

Worked connection: a tiny graph by hand and by autograd — the same chain-rule walk as Section 10

Take a small expression in the same spirit as Section 10's network — multiply two values, add a third, then multiply the result by a fourth. Different numbers from Section 10's sigmoid neuron, but the exact same backward procedure.

$$ e = a \cdot b, \qquad d = e + c, \qquad L = d \cdot f $$

In words: three operations chained together, ending in a single number L. This is a tiny neural network in disguise: a multiply (like a weight times an input), an add (like a bias), then another multiply (like a second layer).

With a = 2, b = -3, c = 10, f = -2, the forward pass gives e = -6, d = 4, L = -8. Now apply the chain rule backward from L, exactly as in Section 10:

$$ \begin{aligned} \frac{\partial L}{\partial d} &= f = -2, &\qquad \frac{\partial L}{\partial f} &= d = 4 \\[4pt] \frac{\partial L}{\partial e} &= \frac{\partial L}{\partial d}\cdot\frac{\partial d}{\partial e} = -2 \cdot 1 = -2, &\qquad \frac{\partial L}{\partial c} &= \frac{\partial L}{\partial d}\cdot\frac{\partial d}{\partial c} = -2 \cdot 1 = -2 \\[4pt] \frac{\partial L}{\partial a} &= \frac{\partial L}{\partial e}\cdot\frac{\partial e}{\partial a} = -2 \cdot b = -2\cdot(-3) = 6, &\qquad \frac{\partial L}{\partial b} &= \frac{\partial L}{\partial e}\cdot\frac{\partial e}{\partial b} = -2 \cdot a = -2\cdot 2 = -4 \end{aligned} $$

In words: start at the output and multiply local derivatives backward along the graph, exactly the chain-rule walk from Section 10. Each variable's gradient is "how much did the final number move, per unit change in me" — a's gradient of 6 means nudging a up by a tiny amount would push L up by about 6 times that amount.

Now build the identical graph in PyTorch and let autograd do the same walk:

import torch

a = torch.tensor(2.0,  requires_grad=True)
b = torch.tensor(-3.0, requires_grad=True)
c = torch.tensor(10.0, requires_grad=True)
f = torch.tensor(-2.0, requires_grad=True)

e = a * b
d = e + c
L = d * f

L.backward()

print(a.grad, b.grad, c.grad, f.grad)
# tensor(6.) tensor(-4.) tensor(-2.) tensor(4.)  <-- identical to the hand derivation above

Same numbers, to the decimal. That's the whole trick of autograd: it is not a different or approximate technique, it is the literal chain-rule walk from Section 10, executed by a machine that never drops a term.

Check yourself In the worked example, why is c.grad exactly equal to e's upstream gradient, both −2? Reveal

Because d = e + c, and the local derivative of a sum with respect to either input is always 1 (∂d/∂e = 1, ∂d/∂c = 1). The chain rule multiplies the upstream gradient by that local derivative, so both e and c simply inherit d's gradient unchanged. Addition never rescales a gradient — it only ever copies it to both of its inputs.

4Graph mechanics: leaves, detaching, and not tracking at all

Intuition first

A few practical rules keep autograd from doing more (or less) work than you want. Knowing them is the difference between code that trains correctly and code that silently accumulates garbage or crashes with a confusing error.

Definition

A leaf tensor is one you created directly (like a and b above) rather than one produced by an operation on other tracked tensors (like e or d). Only leaf tensors accumulate a .grad by default — the model's actual parameters (weights, biases) are always leaves, which is exactly what you want, since those are the numbers you'll update.

Now the math

Two ways to stop autograd from tracking, for different reasons:

  • .detach() — returns the same numbers as a new tensor that is no longer connected to the graph. Use it when you want a value (say, to log or plot) without dragging the whole history of how it was computed along with it.
  • torch.no_grad() — a context manager that turns off graph-building entirely for everything inside it. Use it for inference (making predictions, not training): there's no backward pass coming, so building the graph would only waste memory and time.

The same thing in PyTorch

import torch

w = torch.tensor(1.5, requires_grad=True)
x = torch.tensor(2.0)

y = w * x
print(y.requires_grad)        # True  -- built from a tracked tensor

with torch.no_grad():
    y_infer = w * x           # no graph built at all -- for prediction, not training
    print(y_infer.requires_grad)  # False

y_detached = y.detach()       # same value as y, graph history dropped
print(y_detached.requires_grad)   # False
▲ Gradients accumulate — zero them

Calling .backward() does not overwrite .grad, it adds to whatever was already there. Run the backward pass twice in a row without resetting, and you'll silently add two steps' worth of gradient together — a subtle bug that trains, just wrong. This is why every training loop calls something like optimizer.zero_grad() before each backward pass; we'll wire that into a full loop in Section 14.

x = torch.tensor(2.0, requires_grad=True)

y = x ** 2
y.backward()
print(x.grad)     # tensor(4.)   dy/dx = 2x = 4

y = x ** 2
y.backward()
print(x.grad)     # tensor(8.)   NOT 4 again -- it accumulated: 4 + 4

x.grad.zero_()     # reset before the next backward pass
y = x ** 2
y.backward()
print(x.grad)      # tensor(4.)  correct, now that we cleared it first
Check yourself You call loss.backward() three times in a row on the same weights, forgetting to zero the gradient between calls, where each call would individually produce a gradient of 0.5. What ends up in .grad? Reveal

1.5 — gradients accumulate by addition, so three backward passes of 0.5 each sum to 0.5 + 0.5 + 0.5 = 1.5. If your training loss is doing something inexplicable, "forgot to call zero_grad()" is one of the first things to check.

5What to carry forward

  • A tensor is an n-dimensional array with a shape, dtype, and device — scalar, vector, matrix, or higher, all the same idea.
  • Broadcasting stretches a smaller tensor across a bigger one when their shapes are compatible from the right, no loop required.
  • Autograd builds the same kind of computation graph you built by hand in Section 10, and .backward() runs the exact same chain-rule walk — autograd matched the by-hand gradients above to the decimal.
  • Only leaf tensors (like model parameters) accumulate .grad; use .detach() to drop history and torch.no_grad() for inference.
  • Gradients accumulate across calls to .backward() — always zero them before the next backward pass.
