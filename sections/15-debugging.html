Debugging & Good Habits

Almost every training bug announces itself the same handful of ways — learn to recognize them and a broken run stops being a mystery and becomes a five-minute fix.

22 min read
You'll learn
  • shape discipline
  • gradient checking
  • overfit-a-single-batch
  • logging & checkpointing

Training a neural network fails silently far more often than it fails loudly. The loss doesn't always crash with a red error — sometimes it just quietly refuses to go down, and nothing in the code looks wrong. This section is not theory. It's the exact sequence of checks a working engineer runs, in order, whenever a model isn't learning.

◆ The one idea to hold onto

Debugging a model is not different from debugging any other program — it's just that the failures are quieter. Make them loud on purpose: print shapes, check gradients by hand, and prove the model can learn something trivial before trusting it on something hard.

1Shape discipline: print them everywhere

Intuition first

The single most common bug in any deep learning codebase is a shape mismatch — a tensor coming out of one layer doesn't have the shape the next layer expects. We already met the rule that governs this in Section 1: to multiply an (m × n) matrix by an (n × p) matrix, the inner numbers must match. Every time you write a new layer, model, or loss function, you are betting that this rule holds all the way through. Bet wrong, and PyTorch will tell you — but only if you read the error carefully.

☂ Everyday parallel

It's like plumbing pipes of different diameters. If pipe A ends in a 2-inch opening and pipe B starts with a 3-inch fitting, water doesn't flow — no matter how good either pipe is on its own. A shape mismatch is exactly that: two perfectly correct layers that simply don't connect, because one hands over a different-sized "pipe" than the next one expects.

Reading a real shape error

Say you build a tiny two-layer network, but mistype the input size of the second layer:

import torch.nn as nn

layer1 = nn.Linear(784, 128)   # 784 pixels in, 128 features out
layer2 = nn.Linear(64, 10)     # BUG: should be nn.Linear(128, 10)

x = torch.randn(32, 784)       # a batch of 32 images
h = layer1(x)                  # h has shape (32, 128) -- correct so far
out = layer2(h)                # crashes

what PyTorch actually prints

RuntimeError: mat1 and mat2 shapes cannot be multiplied (32x128 and 64x10)

Read it left to right: mat1 is your data, shape (32, 128) — that's h, exactly as expected. mat2 is the weight matrix inside layer2, and its first number, 64, is wrong: it should have matched h's last dimension, 128. The error message is telling you exactly which two tensors collided and what their shapes were at that moment — it is not a generic complaint, it's a diagnosis, if you read both numbers on each side.

▲ Watch out

Don't guess at a fix by trial and error. Instead, add print(x.shape) after every line that changes a tensor's shape while you're debugging, then delete the prints once the model runs. Five seconds of printing beats twenty minutes of guessing.

Check yourself Using the buggy code above, what one-word change to layer2 fixes it, and why does 128 (not 64 or 10) belong there? Reveal

Change nn.Linear(64, 10) to nn.Linear(128, 10). A nn.Linear(in_features, out_features) layer's first number must match the last dimension of whatever tensor flows into it — here, h has shape (32, 128), so the incoming feature dimension is 128, regardless of what the previous layer's output count happened to be conceptually. The 10 stays as-is; it's the number of classes you want out, unrelated to the mismatch.

2Gradient checking: does the math match reality

Intuition first

Backpropagation (covered in Section 10) computes gradients analytically — by applying calculus rules symbolically. That's fast, but if you've written a custom loss or layer, it's easy to get one sign or one factor wrong. Gradient checking catches this by computing the same gradient a second, much slower way — by literally nudging one number and watching how much the output moves — and comparing the two answers.

☂ Everyday parallel

You calculate a tip in your head (analytic: apply the 15% rule). Then, to double check, you actually add one dollar to the bill and see the total change by roughly the right amount (numeric: nudge and observe). If your mental math and the nudge-and-observe check disagree, trust the nudge — your mental shortcut has a bug in it.

Now the math

The definition of a derivative already tells us how to check it: nudge the input by a tiny amount ε in both directions and see how the loss L moves.

$$ \frac{\partial L}{\partial w} \approx \frac{L(w+\epsilon) - L(w-\epsilon)}{2\epsilon} $$

In words: nudge the weight w up by a tiny amount ε (epsilon) and evaluate the loss; nudge it down by the same tiny amount and evaluate again; the difference, divided by twice the nudge, is an estimate of the slope at that point — the numeric gradient. This uses both sides (a "centered" difference) because it cancels out more error than only nudging one way.

The same thing in PyTorch

import torch

def loss_fn(w):
    return (w ** 2).sum()   # a toy loss; true gradient is 2*w

w = torch.tensor([1.0, 2.0, 3.0], requires_grad=True)

# 1) the analytic gradient, from autograd
loss = loss_fn(w)
loss.backward()
analytic = w.grad.clone()

# 2) the numeric gradient, one entry at a time
eps = 1e-4
numeric = torch.zeros_like(w)
for i in range(len(w)):
    w_plus = w.detach().clone();  w_plus[i]  += eps
    w_minus = w.detach().clone(); w_minus[i] -= eps
    numeric[i] = (loss_fn(w_plus) - loss_fn(w_minus)) / (2 * eps)

print(analytic)   # tensor([2., 4., 6.])
print(numeric)    # tensor([2.0000, 4.0000, 6.0000])  -- matches, within ~eps^2
Check yourself You run this check and the analytic gradient is consistently exactly 1000 times larger than the numeric one, across every entry. What kind of bug does that pattern suggest? Reveal

A random, scattered mistake wouldn't produce a clean, uniform ratio like 1000x on every entry. A constant multiplicative gap points to a scale bug in the analytic path — e.g. the loss is being summed over a batch of 1000 elsewhere without ever averaging, or a manually derived gradient is missing (or double-applying) a constant factor from the chain rule. Look for a stray .sum() that should be .mean(), or a dropped/extra constant in a hand-written derivative.

3The single best debugging test: overfit one batch

Intuition first

Before you trust a model on your real dataset, ask it to do something much easier: memorize one small batch — say, 8 or 16 examples — with nothing held back. Train on that exact same batch for a few hundred steps. A working model and training loop should drive the loss down to nearly zero (or accuracy to 100%) on that tiny batch, because there is nothing to generalize; it just has to remember 16 answers.

☂ Everyday parallel

You don't test a new oven by baking 200 cookies at once. You bake one cookie first. If that one cookie comes out burnt or raw, you don't have a "cookie problem," you have an oven problem — and you'd rather find that out with one cookie than with 200. Overfitting a single batch is baking the one test cookie before you commit the whole tray.

◆ Why this test is so powerful

If the model cannot drive the loss near zero on one tiny, memorizable batch, the bug is almost never about the model being "not powerful enough" or "needing more data." It's a real bug: a wrong loss function, a detached computation graph (gradients silently not flowing), mismatched or shuffled labels, or a learning rate that's absurdly wrong. Find it here, on one batch, in seconds — not three hours into a real training run.

The same thing in PyTorch

model = MyModel()
optimizer = torch.optim.Adam(model.parameters(), lr=1e-3)
criterion = torch.nn.CrossEntropyLoss()

xb, yb = next(iter(train_loader))   # grab ONE batch and reuse it every step

for step in range(300):
    optimizer.zero_grad()
    out = model(xb)
    loss = criterion(out, yb)
    loss.backward()
    optimizer.step()
    if step % 50 == 0:
        print(step, loss.item())

# healthy run: loss falls toward ~0 well before step 300
# broken run: loss plateaus at a stubbornly high value -- go find the bug
Check yourself You run the overfit-one-batch test and the loss drops for a bit, then plateaus at a high value and never gets close to zero, even after 500 steps. Name three concrete things to check. Reveal

(1) Are the labels actually aligned with the inputs — did shuffling or a data pipeline bug scramble xb and yb relative to each other? (2) Is the loss function right for the task (e.g. not using mean-squared-error on raw classification logits, or using the wrong reduction) and is gradient actually flowing — no accidental .detach() or a stray .item()/.data access that cuts the graph? (3) Is the learning rate reasonable — plateauing rather than diverging can mean the learning rate is too small to make progress in the number of steps you gave it.

4Logging and reading loss curves

Intuition first

Once the single-batch test passes, log the loss (and any accuracy metric) every epoch, for both the training set and a held-out validation set, and plot them. The shape of that curve is a diagnosis, not just a number.

☂ Everyday parallel

A doctor doesn't just look at your temperature once — they look at the trend across the day. A fever that's climbing, one that's flat and high, and one that's falling all mean different things and call for different responses. A loss curve is a vital-signs chart for your training run.

What you seeWhat it usually means
Loss stays high, barely movesSomething is fundamentally broken — re-run the overfit-one-batch test if you haven't; also suspect a learning rate that's far too small.
Loss goes up, or to NaNDiverging. Almost always the learning rate is too high, or an unstable operation (e.g. log(0), exploding gradients) is involved. Try lowering the learning rate or adding gradient clipping.
Training loss keeps falling, validation loss flattens or risesA growing gap between train and validation performance — this is overfitting: the model is memorizing the training set instead of learning general patterns.
Both curves fall together and flatten near the same valueHealthy. This is what a well-behaved training run looks like.

minimal logging loop

history = {"train_loss": [], "val_loss": []}

for epoch in range(num_epochs):
    model.train()
    train_loss = run_one_epoch(model, train_loader, optimizer)  # your training step

    model.eval()
    with torch.no_grad():
        val_loss = run_one_epoch(model, val_loader, optimizer=None)  # no update, just measure

    history["train_loss"].append(train_loss)
    history["val_loss"].append(val_loss)
    print(f"epoch {epoch}: train={train_loss:.4f}  val={val_loss:.4f}")

5Checkpointing, and train() vs eval()

Intuition first

A checkpoint is a saved snapshot of your model's learned numbers, so a crashed run — or a finished one — doesn't cost you the training you already did. Saving is only half the story, though: when you load a model back for evaluation, you must also tell it to behave differently than it did during training, using model.eval().

☂ Everyday parallel

Think of a restaurant kitchen during a chaotic dinner rush versus a calm plating for a food photographer. During the rush (training), the kitchen improvises, substitutes ingredients, and varies technique run to run. For the photo (evaluation), everyone follows the exact same, fixed, repeatable steps every time. Same kitchen, same recipe — deliberately different mode.

Saving and loading

torch.save(model.state_dict(), "checkpoint.pt")

model = MyModel()
model.load_state_dict(torch.load("checkpoint.pt"))

Some layers — dropout and batch normalization, covered in Section 20 — behave differently while training than while evaluating. Dropout randomly zeroes units only during training; batch norm uses statistics from the current batch while training, but a running average while evaluating. model.train() and model.eval() are how you tell PyTorch which mode those layers should use — they do not touch the weights, only the behavior of a few specific layer types.

model.train()                 # dropout active; batchnorm uses batch stats
for xb, yb in train_loader:
    ...                        # normal training step

model.eval()                  # dropout off; batchnorm uses running stats
with torch.no_grad():         # also skip building the graph -- we won't call backward()
    preds = model(x_val)
Check yourself You load a checkpoint and run inference, but predictions are noticeably worse and slightly different every time you re-run the exact same input. What did you most likely forget? Reveal

model.eval(). Without it, the model is still in training mode: dropout is randomly zeroing a fraction of units on every call (which explains why the same input gives slightly different outputs each time), and batch normalization is using statistics from whatever small batch you happened to pass in, rather than the stable running averages collected during training. Both effects degrade and randomize predictions in exactly this way.

6The usual suspects: a checklist

When a model won't train, walk this list before anything more exotic:

  • Forgot optimizer.zero_grad(). Gradients accumulate (add up) across calls to backward() by default. Skip the reset and each step's gradient is contaminated by every previous step's.
  • Forgot model.eval() at evaluation time. Dropout and batch norm keep training-time behavior, quietly corrupting validation/test numbers.
  • Learning rate too high. Shows up as a diverging or NaN loss; the fix is almost always to lower it (or warm it up gradually).
  • Wrong loss reduction. Mixing up sum and mean reduction silently rescales your effective learning rate by the batch size.
  • Data on the wrong device. Mixing a CPU tensor with a GPU model (or vice versa) raises a clear error, but forgetting to move a new tensor you created mid-forward pass is an easy miss — watch for RuntimeError: Expected all tensors to be on the same device.

7What to carry forward

  • Print shapes constantly. Most bugs are a shape mismatch, and PyTorch's error message tells you exactly which two tensors collided if you read both sides.
  • Gradient checking compares the analytic gradient (from backward()) against a numeric one from nudging weights by ε — use it whenever you write a custom loss or layer.
  • Overfit one small batch first. If the loss won't go near zero on a batch of 16, the bug is in your code, not your data or your model's capacity.
  • Log train and validation curves every epoch; a growing gap between them means overfitting, a flat high loss means something is broken, a rising loss means the learning rate is too high.
  • Checkpoint with state_dict(), and always pair loading a model with the right model.train() / model.eval() call.
