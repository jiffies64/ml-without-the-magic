Debugging & Good Habits

Most training bugs show up in a few typical ways. Learn to recognize them, and a broken run becomes a problem you can find and fix.

38 min read
You'll learn
  • shape discipline
  • gradient checking
  • overfit-a-single-batch
  • logging & checkpointing

A neural network that fails to train usually fails without an error message. The loss does not crash with a red error. It stops going down, and nothing in the code looks wrong. This section is practical, not theory. It gives the sequence of checks to run, in order, when a model is not learning.

◆ The one idea to hold onto

Debugging a model is like debugging any other program, except that the failures are silent. So make them visible on purpose. Print shapes, check gradients numerically, and prove that the model can learn something easy before you trust it with something hard.

1Shape discipline: print them everywhere

Intuition first

A very common bug in deep learning code is a shape mismatch. A tensor that comes out of one layer does not have the shape the next layer expects. We met the rule behind this in Section 1. To multiply an $(m \times n)$ matrix by an $(n \times p)$ matrix, the inner numbers must match. Every new layer, model or loss function depends on this rule holding all the way through. When it fails, PyTorch tells you, and the error message says where.

☂ Everyday parallel

Think of water pipes of different diameters. Pipe A ends in a 5 cm opening, and pipe B starts with an 8 cm fitting. They do not connect, however good each pipe is. A shape mismatch is the same: two correct layers that do not connect, because one delivers a different size than the next one accepts.

The same thing in PyTorch

Say you build a tiny two-layer network, but you type the wrong input size for the second layer:

a two-layer network with a wrong input size

import torch
import torch.nn as nn

layer1 = nn.Linear(784, 128)   # 784 pixels in, 128 features out
layer2 = nn.Linear(64, 10)     # BUG: should be nn.Linear(128, 10)

x = torch.randn(32, 784)       # a batch of 32 images
h = layer1(x)                  # h has shape (32, 128) -- correct so far
out = layer2(h)                # crashes

what PyTorch prints

RuntimeError: mat1 and mat2 shapes cannot be multiplied (32x128 and 64x10)

Read it from left to right. mat1 is your data, h. Its shape is (32, 128), as expected. mat2 comes from the weight of layer2. nn.Linear stores its weight as (out, in), here (10, 64), and multiplies by its transpose, (64, 10). That is what the message shows. Its first number, 64, should match h's last dimension, 128. So the message is a diagnosis, not a general complaint. Read both numbers on each side.

▲ Watch out

Do not guess a fix by trial and error. While you debug, add print(x.shape) after every line that changes a tensor's shape. Delete the prints once the model runs. A few seconds of printing saves many minutes of guessing.

▲ Watch out

Some shape bugs raise no error at all, because of broadcasting (Section 13). If predictions have shape (N, 1) and targets have shape (N,), then pred - y has shape (N, N). The loss is then a wrong number, with no error. In the example below the predictions are perfect, but the loss is 2.5 instead of 0. (F.mse_loss gives a warning in this case; a hand-written loss does not.)

a silent broadcasting bug in a loss

import torch

pred = torch.tensor([[1.0], [2.0], [3.0], [4.0]])   # shape (4, 1): perfect predictions
y = torch.tensor([1.0, 2.0, 3.0, 4.0])              # shape (4,)

print((pred - y).shape)                        # torch.Size([4, 4])  -- not (4,)!
print(((pred - y) ** 2).mean())                # tensor(2.5000)  wrong
print(((pred.squeeze(1) - y) ** 2).mean())     # tensor(0.)      right
Check yourself In the buggy network, you fix layer2 and then add layer3 = nn.Linear(10, 5) after it. What shape does layer3(layer2(h)) have, and what is the shape of layer3.weight? Reveal

After the fix, layer2 = nn.Linear(128, 10) maps (32, 128) to (32, 10). layer3 maps that to (32, 5). Its weight is stored as (out, in) = (5, 10). The batch size 32 passes through every layer unchanged; only the last dimension changes.

2Gradient checking: does the math match reality?

Intuition first

Backpropagation (Section 10) computes gradients analytically, by applying calculus rules. That is fast. But if you write a custom loss or layer with its own backward pass, it is easy to get one sign or one factor wrong. Gradient checking computes the same gradient a second, much slower way: it changes one number by a tiny amount and measures how much the output moves. Then it compares the two answers. Section 10 introduced this check (see its section 6); here we run it in PyTorch.

☂ Everyday parallel

You compute a 15% tip in your head with a shortcut rule (the analytic way). To check it, you add one dollar to the bill. Then you see whether the tip goes up by about 15 cents. This is the numeric way: change the input and observe. If the two disagree, trust the direct check. Your shortcut has a mistake in it.

Now the math

The definition of the derivative tells us how to check it. Change the input by a tiny amount $\epsilon$ in both directions and see how the loss $L$ moves:

$$ \frac{\partial L}{\partial w} \approx \frac{L(w+\epsilon) - L(w-\epsilon)}{2\epsilon} $$

In words: raise the weight $w$ by a tiny amount $\epsilon$ (epsilon) and compute the loss. Lower it by the same amount and compute the loss again. The difference, divided by $2\epsilon$, estimates the slope at that point: the numeric gradient. Using both sides (a “centered” difference) cancels more of the error than a one-sided nudge. Its error shrinks like $\epsilon^2$ (see Section 10).

Run the check in float64. In float32, the rounding error of each loss value (about $10^{-7}$ relative) is divided by the tiny $2\epsilon$ and becomes large. With float32 and $\epsilon = 10^{-4}$, the check below gives about [2.0027, 4.0007, 5.9938] instead of [2, 4, 6].

The same thing in PyTorch

a numeric gradient check in float64

import torch

def loss_fn(w):
    return (w ** 2).sum()   # a toy loss; the true gradient is 2*w

w = torch.tensor([1.0, 2.0, 3.0], dtype=torch.float64, requires_grad=True)

# 1) the analytic gradient, from autograd
loss = loss_fn(w)
loss.backward()
analytic = w.grad.clone()

# 2) the numeric gradient, one entry at a time
eps = 1e-6
numeric = torch.zeros_like(w)
for i in range(len(w)):
    w_plus = w.detach().clone();  w_plus[i]  += eps
    w_minus = w.detach().clone(); w_minus[i] -= eps
    numeric[i] = (loss_fn(w_plus) - loss_fn(w_minus)) / (2 * eps)

print(analytic)   # tensor([2., 4., 6.], dtype=torch.float64)
print(numeric)    # tensor([2.0000, 4.0000, 6.0000], dtype=torch.float64)
print((analytic - numeric).abs().max().item())   # about 8e-10: they agree

For a real model, PyTorch has a ready-made version of this check: torch.autograd.gradcheck. It also expects float64 inputs.

Check yourself You wrote a custom layer with a hand-written backward pass. The analytic gradient is 1000 times larger than the numeric one, for every entry. The loss averages over a batch of 1000. Where is the bug: in the loss, or in your backward code? Reveal

In your hand-written backward code. The numeric check calls the same loss function. So if the loss used .sum() instead of .mean(), both gradients would grow by 1000 together and still agree. A constant ratio on every entry means the analytic path has a scale bug. Most likely your backward pass forgets the $1/N$ from the mean (with $N = 1000$). Or it applies a constant factor that should not be there.

3A strong debugging test: overfit one batch

Intuition first

Before you trust a model on your real dataset, give it a much easier task. Ask it to memorize one small batch (8 or 16 examples) and train on that same batch for a few hundred steps. A working model and training loop should drive the loss close to zero (or accuracy to 100%) on that batch. There is nothing to generalize; the model only has to remember 16 answers.

☂ Everyday parallel

Before a long car trip, you drive once around the block. If the car cannot even do that, the problem is not the long road; it is the car. You would rather find that out near home than halfway through the trip. Overfitting one batch is the drive around the block.

◆ Why this test is so useful

Suppose the model cannot drive the loss near zero on one tiny batch. Then the problem is almost never that the model is too small or needs more data. It is a real bug. Typical causes are the wrong loss function or a detached computation graph (so gradients do not flow). Others are labels that do not match their inputs, or a learning rate that is far off. You find it here, on one batch, in seconds, and not hours into a real training run.

The same thing in PyTorch

train on one fixed batch until the loss is near zero

import torch
import torch.nn as nn

torch.manual_seed(0)
model = nn.Sequential(nn.Linear(20, 64), nn.ReLU(), nn.Linear(64, 5))
optimizer = torch.optim.Adam(model.parameters(), lr=1e-3)
criterion = nn.CrossEntropyLoss()

xb = torch.randn(16, 20)            # ONE batch of 16 examples...
yb = torch.randint(0, 5, (16,))     # ...with 5 classes; reuse it every step
# (with real data: xb, yb = next(iter(train_loader)))

for step in range(301):
    optimizer.zero_grad()
    loss = criterion(model(xb), yb)
    loss.backward()
    optimizer.step()
    if step % 100 == 0:
        print(step, f"{loss.item():.4f}")
# 0 1.5749
# 100 0.2215
# 200 0.0356
# 300 0.0143     healthy: the loss goes toward 0
# A broken run stays at a high value -- go and find the bug.
Check yourself You run the overfit-one-batch test. The loss drops for a while, then stays at a high value and never gets close to zero, even after 500 steps. Name three concrete things to check. Reveal

(1) Do the labels match the inputs? A data-pipeline bug can shuffle xb and yb separately. (2) Is the loss right for the task, and do gradients flow? For example, do not pass softmax outputs to CrossEntropyLoss, and look for an accidental .detach(), .item() or .data that cuts the graph. (3) Is the learning rate reasonable? A loss that stays flat (rather than diverging) can mean the learning rate is too small for the number of steps.

4Logging and reading loss curves

Intuition first

Once the single-batch test passes, log the loss (and any accuracy metric) every epoch. Do it for both the training set and a held-out validation set, and plot them. The shape of the curve is a diagnosis, not only a number.

☂ Everyday parallel

A doctor does not look at your temperature only once. The doctor looks at the trend over the day. A fever that is rising, one that stays high, and one that is falling mean different things and need different responses. A loss curve is the same kind of chart for your training run.

What you seeWhat it usually means
(a) Loss stays high, barely movesSomething is broken. Run the overfit-one-batch test if you have not. Also suspect a learning rate that is far too small.
(b) Loss goes up, or to NaNDiverging. Usually the learning rate is too high, or an unstable operation is involved (for example log(0), or exploding gradients). Lower the learning rate or add gradient clipping.
(c) Training loss keeps falling, validation loss flattens or risesA growing gap between training and validation: overfitting. The model memorizes the training set instead of learning general patterns (Section 7).
(d) Both curves fall together and flatten near the same valueHealthy. This is what a well-behaved training run looks like.

The same thing in PyTorch

a minimal logging loop on a toy problem

import torch
import torch.nn as nn
from torch.utils.data import DataLoader, TensorDataset

torch.manual_seed(0)
X = torch.randn(600, 20)
y = (X[:, 0] + 0.5 * torch.randn(600) > 0).long()     # a learnable toy label
train_loader = DataLoader(TensorDataset(X[:500], y[:500]), batch_size=32, shuffle=True)
val_loader = DataLoader(TensorDataset(X[500:], y[500:]), batch_size=100)
model = nn.Sequential(nn.Linear(20, 64), nn.ReLU(), nn.Linear(64, 2))
optimizer = torch.optim.Adam(model.parameters(), lr=1e-3)
loss_fn = nn.CrossEntropyLoss()

def run_one_epoch(model, loader, optimizer=None):
    total, count = 0.0, 0
    for xb, yb in loader:
        loss = loss_fn(model(xb), yb)
        if optimizer is not None:            # training: update the weights
            optimizer.zero_grad()
            loss.backward()
            optimizer.step()
        total += loss.item() * len(yb)
        count += len(yb)
    return total / count                     # average loss per example

history = {"train_loss": [], "val_loss": []}
for epoch in range(5):
    model.train()
    train_loss = run_one_epoch(model, train_loader, optimizer)
    model.eval()
    with torch.no_grad():
        val_loss = run_one_epoch(model, val_loader)   # no optimizer: only measure
    history["train_loss"].append(train_loss)
    history["val_loss"].append(val_loss)
    print(f"epoch {epoch}: train={train_loss:.4f}  val={val_loss:.4f}")

output

epoch 0: train=0.6949  val=0.6849
epoch 1: train=0.6518  val=0.6541
epoch 2: train=0.6198  val=0.6243
epoch 3: train=0.5864  val=0.5944
epoch 4: train=0.5530  val=0.5646

Both losses fall together, so this run looks like pattern (d) so far. It has not converged yet; more epochs would help.

Check yourself After 50 epochs, the training loss is 0.05 and still falling. The validation loss reached its lowest value, 0.40, at epoch 18 and has risen to 0.65 since. Which pattern is this, and which checkpoint would you keep? Reveal

Pattern (c), overfitting. The model got better on unseen data until epoch 18; after that it memorized the training set. Keep the checkpoint from epoch 18, where the validation loss was lowest. (This is “early stopping.”) To do better, add regularization or more data.

5Checkpointing, and train() vs eval()

Intuition first

A checkpoint is a saved snapshot of your model's learned numbers. If a run crashes, or when it finishes, you do not lose the training you already did. Saving is only half of the job. When you load a model to evaluate it, you must also tell it to behave differently than during training, with model.eval().

☂ Everyday parallel

Think of a theater group. In rehearsals, the director swaps in random understudies for some roles, so that no actor depends too much on one partner. On opening night, the full regular cast plays every role, the same way every night. Training mode is rehearsal (dropout switches off random units). Evaluation mode is opening night: the full network, every time.

The same thing in PyTorch

save and load a checkpoint (continues the logging loop above)

torch.save({"epoch": epoch,
            "model": model.state_dict(),
            "optimizer": optimizer.state_dict()},   # Adam's m and v, step counts
           "checkpoint.pt")

# later, or in a new program: build the same objects, then load the numbers
ckpt = torch.load("checkpoint.pt")
model = nn.Sequential(nn.Linear(20, 64), nn.ReLU(), nn.Linear(64, 2))
optimizer = torch.optim.Adam(model.parameters(), lr=1e-3)
model.load_state_dict(ckpt["model"])
optimizer.load_state_dict(ckpt["optimizer"])
start_epoch = ckpt["epoch"] + 1     # 5: continue where we stopped

Save the optimizer state too if you want to continue training. Adam keeps its running averages $m$ and $v$ for every parameter (Section 12). If you restart with a fresh optimizer, those averages start again at zero, and the first steps after the restart behave differently.

Some layers behave differently in training and in evaluation. Two common ones are dropout and batch normalization (Section 20). Dropout sets random units to zero, but only during training. Batch norm uses statistics of the current batch during training, and a running average during evaluation. model.train() and model.eval() tell PyTorch which mode to use. They do not change the weights; they change only the behavior of a few layer types.

dropout in training mode and in evaluation mode

import torch
import torch.nn as nn

torch.manual_seed(0)
net = nn.Sequential(nn.Linear(4, 8), nn.ReLU(), nn.Dropout(p=0.5), nn.Linear(8, 1))
x = torch.randn(1, 4)

net.train()                   # dropout active: random units are zeroed
print(net(x).item(), net(x).item())   # -0.1568 -0.1155  (different each call)

net.eval()                    # dropout off; batchnorm would use running stats
with torch.no_grad():         # also skip building the graph: no backward() follows
    print(net(x).item(), net(x).item())   # -0.1362 -0.1362  (the same every call)
Check yourself You load a checkpoint and run inference. The predictions are worse than expected, and they change a little each time you run the same input. What did you most likely forget? Reveal

model.eval(). Without it, the model is still in training mode. Dropout sets random units to zero on every call, so the same input gives different outputs. Batch normalization uses the statistics of the small batch you passed in, not the stable running averages from training. Both effects make predictions worse and random.

6The usual suspects: a checklist

When a model does not train, go through this list before you look for anything unusual:

  • Forgot optimizer.zero_grad(). By default, gradients accumulate (add up) across calls to backward(). If you skip the reset, each step's gradient includes every earlier step's gradient.
  • Forgot model.eval() for evaluation. Dropout and batch norm keep their training behavior and distort the validation and test numbers.
  • Learning rate too high. It shows as a diverging or NaN loss. The fix is usually to lower it (or to warm it up slowly).
  • Wrong loss reduction. With sum instead of mean, the gradient is $N$ times larger ($N$ = batch size). With SGD this acts like an $N$ times higher learning rate. With Adam it has almost no effect, because Adam divides out the gradient's scale.
  • Silent broadcasting. A (N, 1) prediction against a (N,) target gives an (N, N) loss matrix and no error (section 1).
  • Data on the wrong device. Mixing a CPU tensor with a GPU model raises a clear error. But a new tensor that you create inside forward is easy to miss. Watch for RuntimeError: Expected all tensors to be on the same device, and create such tensors with device=x.device.
Check yourself Find the bug: for xb, yb in loader: loss = loss_fn(model(xb), yb); loss.backward(); optimizer.step(). The model trains well for a few steps, then the loss jumps around and grows. Why? Reveal

There is no optimizer.zero_grad(). Each backward() adds to the gradients already in .grad. After $k$ steps, .grad holds the sum of $k$ batch gradients, so the steps grow and point partly in old directions. At first the error is small, which is why the first steps look fine. Add optimizer.zero_grad() at the top of the loop.

7What to carry forward

  • Print shapes often. When shapes do not match, PyTorch's error message names the two tensors that failed to combine. Read both sides. Also watch for silent broadcasting.
  • Gradient checking compares the analytic gradient (from backward()) with a numeric one, from changing weights by $\pm\epsilon$. Run it in float64 whenever you write a custom backward pass.
  • Overfit one small batch first. If the loss does not go near zero on a batch of 16, the bug is in your code. It is not in your data or in the size of your model.
  • Log training and validation curves every epoch. A growing gap between them means overfitting. A flat, high loss means something is broken. A rising loss means the learning rate is too high.
  • Checkpoint the model's and the optimizer's state_dict(). Use model.eval() to evaluate and model.train() to train.
