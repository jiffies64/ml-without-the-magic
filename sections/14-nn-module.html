nn.Module & the Training Loop

Five calls (zero_grad, forward, loss, backward, step) train every PyTorch model. Once you can explain each one, you can read other people's training code.

30 min read
You'll learn

You now know tensors and autograd. You can build a computation graph and get gradients from it. nn.Module is a clean way to organize many such graphs (the weights, the layers, the forward computation) into one reusable object. From here on, the new ideas are about organization, not new math.

◆ The one idea to hold onto

nn.Module is a box that remembers its own parameters and knows how to compute its own output. The training loop is a short, fixed procedure. It feeds data through that box again and again, measures how wrong the output is, and moves the parameters to make it less wrong. Every PyTorch project is built on these two ideas.

1nn.Module: a container that tracks its own parts

Intuition first

nn.Module is PyTorch's base class for “a thing that has learnable numbers and a way to use them.” You write a subclass of it. You declare your layers in __init__, and you write how data flows through them in forward. In return, PyTorch finds every parameter you declared, however deeply nested. You never have to keep a list of them by hand.

☂ Everyday parallel

Lego bricks. A single brick (one nn.Linear layer) does one small thing. Connect several bricks in a fixed order and you get something bigger, such as a wall or a car. nn.Module is both the brick and the rule for connecting bricks. A module can contain other modules, and from the outside the result looks like one bigger module.

Now the math

A tiny MLP (multi-layer perceptron: linear layers with a nonlinearity between them) with one hidden layer computes:

$$ \mathbf{h} = \phi(\mathbf{W}_1\mathbf{x} + \mathbf{b}_1), \qquad \hat{\mathbf{y}} = \mathbf{W}_2\mathbf{h} + \mathbf{b}_2 $$

In words: transform the input $\mathbf{x}$ with the first layer's weights and bias. Pass the result through a nonlinearity $\phi$ (here ReLU), so the network can learn curves, not only straight lines. Then transform the hidden result $\mathbf{h}$ with a second layer to get the prediction $\hat{\mathbf{y}}$. Each $\mathbf{W}$ and $\mathbf{b}$ is a learnable leaf tensor, as in Section 13. $\mathbf{W}_1$ has shape (out, in), like every nn.Linear weight.

The same thing in PyTorch

a two-layer MLP as an nn.Module

import torch
import torch.nn as nn

class TinyMLP(nn.Module):
    def __init__(self, in_features, hidden, out_features):
        super().__init__()                          # required: sets up PyTorch's bookkeeping
        self.layer1 = nn.Linear(in_features, hidden)  # holds W1, b1 -- created and tracked for you
        self.act    = nn.ReLU()                       # the nonlinearity phi
        self.layer2 = nn.Linear(hidden, out_features) # holds W2, b2

    def forward(self, x):
        h = self.act(self.layer1(x))   # h = phi(W1 x + b1)
        return self.layer2(h)          # y_hat = W2 h + b2

model = TinyMLP(in_features=784, hidden=64, out_features=10)

x = torch.randn(32, 784)   # a batch of 32 flattened 28x28 images
y_hat = model(x)           # calls forward() for you
print(y_hat.shape)         # torch.Size([32, 10])

for name, p in model.named_parameters():
    print(name, p.shape)   # found automatically:
# layer1.weight torch.Size([64, 784])
# layer1.bias torch.Size([64])
# layer2.weight torch.Size([10, 64])
# layer2.bias torch.Size([10])
Definition

Calling model(x) runs forward. Do not call model.forward(x) directly. model(x) goes through __call__, which also runs some bookkeeping (like hooks) that a direct call would skip.

Check yourself A classmate writes h = nn.Linear(784, 64)(x) inside forward instead of creating self.layer1 in __init__. The code runs. What goes wrong during training? Reveal

Every forward pass creates a brand-new layer with new random weights. Those weights are not attributes of the module, so model.parameters() does not list them and the optimizer never updates them. Even if it did, they would be thrown away at the next call. So the first layer never learns. Parameters must be created once, as attributes in __init__, so they persist and can be found.

2Dataset & DataLoader: feeding the model in small batches

Intuition first

A Dataset is an object that knows two things: how many examples it has, and how to fetch the n-th one. A DataLoader wraps it and does the detailed work. It groups examples into minibatches. It shuffles their order each epoch (one full pass over the data). And it gives you one batch at a time in a simple loop.

☂ Everyday parallel

A Dataset is a filing cabinet of numbered cards: ask for card 47 and you get it. A DataLoader is an assistant. At the start of each round, the assistant decides a new random order for the cards. Then the assistant hands you the cards in small stacks, in that order, until every card has been used once. You only say “next stack, please.”

Why use small stacks instead of all the data at once? As Section 12 explained, the exact gradient over the whole dataset is slow and uses a lot of memory. A minibatch (a random, modest-sized part of the data) gives a noisy but cheap estimate of that gradient. Many small, noisy steps usually reach a good model faster than a few exact ones.

The same thing in PyTorch

a Dataset and a DataLoader

import torch
from torch.utils.data import Dataset, DataLoader

class ToyDataset(Dataset):
    def __init__(self, X, y):
        self.X, self.y = X, y

    def __len__(self):
        return len(self.X)               # how many examples in total

    def __getitem__(self, idx):
        return self.X[idx], self.y[idx]  # one example, by index

torch.manual_seed(0)
X = torch.randn(1000, 784)         # 1000 fake flattened images
y = torch.randint(0, 10, (1000,))  # 1000 fake labels, classes 0-9

dataset = ToyDataset(X, y)
loader = DataLoader(dataset, batch_size=32, shuffle=True)

for batch_x, batch_y in loader:
    print(batch_x.shape, batch_y.shape)   # torch.Size([32, 784]) torch.Size([32])
    break
Check yourself The dataset has 1,000 examples and batch_size=32. How many batches are in one epoch, and how big is the last one? Why do we shuffle for training but not for validation? Reveal

$1000 / 32 = 31.25$, so there are 32 batches: 31 full ones and a last one with $1000 - 31 \cdot 32 = 8$ examples (len(loader) is 32). Shuffling in training stops the model from learning anything about the order of the examples (for example, if all class-0 examples came first). It also gives each epoch different batches. In validation we update no weights; we only measure. The order does not change the result, and a fixed order makes runs easier to compare.

3The standard training loop

Intuition first

Every PyTorch training script, however large the model, repeats the same few lines. Take a batch. Make a guess. Measure how wrong the guess was. Work out how to improve. Take a small step in that direction. Below is the whole loop, with every line explained. Learn this shape well: you will write a version of it in every project.

☂ Everyday parallel

Learning to throw darts. Throw (forward pass). See how far you missed the center (loss). Work out which way your arm was off, and by how much (backward pass). Adjust your stance a little (optimizer step). Throw again, many times. Training does the same with the data. One pass through all the examples is an epoch. The next epoch uses the same examples again, in a new order. The adjustments stay small, so each throw improves your aim a little.

Now the math

Each step moves every parameter $\theta$ a small amount against its gradient. With plain SGD (from Section 12) the update is:

$$ \theta \leftarrow \theta - \alpha \, \nabla_\theta L $$

In words: for each parameter, subtract the learning rate $\alpha$ times its gradient. optim.SGD performs this line for every parameter at once. The loop below uses optim.Adam, which does a scaled version: it steps along $\hat{m}/(\sqrt{\hat{v}}+\epsilon)$ instead of the raw gradient. Autograd supplies the gradient either way.

The same thing in PyTorch

the training loop (continues the TinyMLP and DataLoader snippets above)

import torch.optim as optim

torch.manual_seed(0)
model = TinyMLP(in_features=784, hidden=64, out_features=10)
loss_fn = nn.CrossEntropyLoss()     # multi-class loss: softmax + log-loss in one step
optimizer = optim.Adam(model.parameters(), lr=1e-3)  # Adam, from Section 12

for epoch in range(3):                       # one full pass over the data
    for batch_x, batch_y in loader:          # one minibatch at a time
        optimizer.zero_grad()                # 1. clear old gradients (see below)
        y_hat = model(batch_x)               # 2. forward pass: raw scores (logits)
        loss = loss_fn(y_hat, batch_y)       # 3. how wrong was the guess? one number
        loss.backward()                      # 4. backward pass: fills .grad for every parameter
        optimizer.step()                     # 5. move every parameter using its .grad

    print(f"epoch {epoch}: loss = {loss.item():.4f}")   # loss of the last batch
# epoch 0: loss = 2.3341
# epoch 1: loss = 1.9191
# epoch 2: loss = 1.4914

The labels here are random, so the falling loss only shows that the model is memorizing the 1,000 training examples. On validation data it cannot do better than chance, as we will see below.

▲ Watch out

nn.CrossEntropyLoss wants the raw scores (logits) from the last layer. It applies the softmax itself, in a numerically stable way. In Section 11 we applied the softmax by hand. Do not do that here: if you pass softmax outputs, the softmax is applied twice. The model still trains, but badly.

▲ Watch out

Why does zero_grad() come first? As you saw in Section 13, .backward() adds to the gradient already in .grad; it never overwrites it. Without optimizer.zero_grad(), each batch's gradient would be added to the last one, and the optimizer would step on the wrong numbers. Clearing the gradients before every backward pass makes each step depend only on the current batch.

Here is a summary of the five calls:

LineWhat it does
optimizer.zero_grad()Clears every parameter's .grad (sets it to None) before this batch.
y_hat = model(batch_x)Forward pass: runs forward() and builds the computation graph.
loss = loss_fn(y_hat, batch_y)Compares the guess to the true labels and gives one number to minimize.
loss.backward()Backward pass: walks the graph and fills .grad on every parameter.
optimizer.step()Uses each parameter's new .grad to update it (with Adam's rule here).

Measuring on validation data

To check how well the model does on data it has not trained on, run a separate loop. Two things change. First, model.eval() switches some layers (such as dropout and batch normalization) to their evaluation behavior. Our TinyMLP has none, but the habit matters. Second, torch.no_grad() stops autograd from building a graph, because no backward pass follows.

an evaluation loop (continues the training loop above)

val_set = ToyDataset(torch.randn(200, 784), torch.randint(0, 10, (200,)))
val_loader = DataLoader(val_set, batch_size=64, shuffle=False)

model.eval()                        # evaluation behavior for dropout, batchnorm, ...
correct, total = 0, 0
with torch.no_grad():               # no graph, no .grad: faster, less memory
    for batch_x, batch_y in val_loader:
        logits = model(batch_x)
        correct += (logits.argmax(dim=1) == batch_y).sum().item()
        total += len(batch_y)
print(f"val accuracy = {correct / total:.3f}")   # val accuracy = 0.110  (chance is 0.1)
model.train()                       # back to training behavior before the next epoch
Check yourself You swap two lines, so each iteration runs zero_grad(), forward, loss, step(), then backward(). What happens to the model? Reveal

It never changes. Since PyTorch 2.0, zero_grad() sets every .grad to None by default. When step() runs next, it finds no gradient and skips every parameter. Then backward() fills .grad, but the next zero_grad() clears it before any step can use it. The loss is printed every epoch, but the weights stay at their initial values. The order forward → loss → backward → step is required, because each call uses what the previous one wrote.

4GPU basics: same code, different device

Intuition first

A GPU (graphics processing unit) does the same tensor arithmetic as a CPU. But it has thousands of small cores that work in parallel, instead of a few fast ones. That gives a large speedup for the big matrix multiplications that neural networks do all the time. Moving your model to a GPU does not change the code above. It only changes where the numbers are stored.

☂ Everyday parallel

A CPU is like a few expert mathematicians who can each solve any problem. A GPU is like a stadium of students who can each only multiply and add. For one hard problem, the experts are better. For a million small multiplications, the stadium finishes first, because everyone works at the same time. Matrix multiplication is that kind of job: the same simple operation, repeated a very large number of times.

◆ The one rule that matters

A tensor on the CPU and a tensor on the GPU cannot be combined in one operation; PyTorch raises an error. The model's parameters and the data you feed it must be on the same device. Move both.

The same thing in PyTorch

training on the GPU when one is available (continues the snippets above)

device = "cuda" if torch.cuda.is_available() else "cpu"

model = TinyMLP(in_features=784, hidden=64, out_features=10).to(device)
optimizer = optim.Adam(model.parameters(), lr=1e-3)   # build it AFTER the model

for batch_x, batch_y in loader:
    batch_x = batch_x.to(device)   # data must move too, every batch
    batch_y = batch_y.to(device)

    optimizer.zero_grad()
    y_hat = model(batch_x)         # model and data are both on `device`
    loss = loss_fn(y_hat, batch_y)
    loss.backward()
    optimizer.step()

Note the order. The optimizer holds references to the parameters it was given. If you build a new model, you must build a new optimizer for it. An optimizer made for an old model updates the old model's parameters, so the new one never trains. Creating the optimizer after .to(device) is the safe habit.

▲ Watch out

The device error you will see first: RuntimeError: Expected all tensors to be on the same device, but found at least two devices, cuda:0 and cpu! You moved the model but not the batch, or the reverse. The fix: find the tensor on the wrong device and add .to(device).

Check yourself You call model.to("cuda") once before training, but inside the loop you forget to move batch_x and batch_y. What happens? Reveal

The forward pass raises the device-mismatch RuntimeError above. The first layer's weights are on the GPU, and the batch is on the CPU. Moving the model once is not enough. Every batch from the DataLoader starts on the CPU and must be moved in every iteration.

5What to carry forward

  • nn.Module is a container. Declare layers in __init__, define the computation in forward, and PyTorch finds every parameter for you.
  • Dataset answers “how many, and give me item i.” DataLoader turns that into shuffled minibatches.
  • The training loop is always zero_grad → forward → loss → backward → step. Zeroing first matters because gradients accumulate. Feed CrossEntropyLoss raw logits.
  • For evaluation, use model.eval() and torch.no_grad(), then switch back with model.train().
  • GPU basics: .to(device) moves tensors. Model and data must be on the same device, and the optimizer must be built for the model you train.
