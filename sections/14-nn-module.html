nn.Module & the Training Loop

Six lines — zero_grad, forward, loss, backward, step — are the entire engine behind every PyTorch model you will ever train; once you can annotate every line, you can read anyone's code.

26 min read You'll learn: nn.Module · Dataset & DataLoader · the canonical training loop · GPU basics

You now know tensors and autograd cold: you can build a computation graph and get gradients out of it. nn.Module is nothing more than a tidy way to organize many such graphs — the weights, the layers, the forward computation — into a reusable object. Everything from here on is organization, not new math.

◆ The one idea to hold onto

nn.Module is a box that remembers its own parameters and knows how to compute its own output. The training loop is a short, fixed recipe that repeatedly feeds data through that box, measures how wrong it was, and nudges the parameters to be less wrong. Nothing in a PyTorch project is more important than these two ideas.

1nn.Module: a container that tracks its own parts

Intuition first

nn.Module is PyTorch's base class for "a thing that has learnable numbers and a way to use them." You subclass it, declare your layers in __init__, and write how data flows through them in forward. In return, PyTorch automatically finds every parameter you declared — no matter how deeply nested — so you never have to track them by hand.

☂ Everyday parallel

Lego blocks. A single brick (one nn.Linear layer) does one small thing. Snap several bricks together in a fixed order and you get something bigger — a wall, a car, a model. nn.Module is both the brick and the rule for snapping bricks together: a module can contain other modules, and the outside world just sees one bigger module.

Now the math

A tiny MLP (multi-layer perceptron, a stack of linear layers with a nonlinearity between them) with one hidden layer computes:

$$ \mathbf{h} = \sigma(\mathbf{W}_1\mathbf{x} + \mathbf{b}_1), \qquad \hat{\mathbf{y}} = \mathbf{W}_2\mathbf{h} + \mathbf{b}_2 $$

In words: transform the input x with the first layer's weights and bias, squash it through a nonlinearity σ (so the network can learn curves, not just straight lines), then transform that hidden result with a second layer to get the prediction ŷ. Each W and b here is exactly the kind of leaf, learnable tensor from Section 13.

The same thing in PyTorch

a two-layer MLP as an nn.Module

import torch
import torch.nn as nn

class TinyMLP(nn.Module):
    def __init__(self, in_features, hidden, out_features):
        super().__init__()                          # required: wires up PyTorch's bookkeeping
        self.layer1 = nn.Linear(in_features, hidden)  # holds W1, b1 -- created and tracked for you
        self.act    = nn.ReLU()                       # the nonlinearity sigma
        self.layer2 = nn.Linear(hidden, out_features) # holds W2, b2

    def forward(self, x):
        h = self.act(self.layer1(x))   # h = sigma(W1 x + b1)
        return self.layer2(h)          # y_hat = W2 h + b2

model = TinyMLP(in_features=784, hidden=64, out_features=10)

x = torch.randn(32, 784)   # a batch of 32 flattened 28x28 images
y_hat = model(x)            # calls forward() under the hood
print(y_hat.shape)           # torch.Size([32, 10])

for name, p in model.named_parameters():
    print(name, p.shape)     # layer1.weight, layer1.bias, layer2.weight, layer2.bias -- found automatically
Definition

Calling model(x) is what actually runs forward — never call model.forward(x) directly. The wrapper that __call__ provides also handles some bookkeeping (like hooks) that you'd otherwise skip.

Check yourself Why must self.layer1 = nn.Linear(...) be assigned as an attribute inside __init__, rather than created fresh inside forward every call? Reveal

Because nn.Module discovers its parameters by scanning the attributes set in __init__. If you built a fresh nn.Linear inside forward, you'd get brand-new, randomly initialized weights on every single forward pass — nothing would ever be learned, since the "same" weights you trained a moment ago would already be gone. The weights have to persist as attributes of the module to be found by .parameters() and updated by the optimizer.

2Dataset & DataLoader: feeding the model in bite-sized batches

Intuition first

A Dataset is just an object that knows two things: how many examples it has, and how to fetch the n-th one. A DataLoader wraps it and handles the fiddly parts — grouping examples into minibatches, shuffling their order each epoch, and handing you one batch at a time in a simple loop.

☂ Everyday parallel

A Dataset is a filing cabinet of index cards — ask for card #47 and you get it. A DataLoader is the assistant who grabs a random handful of cards at a time, hands you that stack, shuffles the cabinet's order overnight, and repeats. You never touch the cabinet directly; you just say "next stack, please."

Why bother with small stacks instead of processing everything at once? As covered in Section 12, computing the exact gradient over the entire dataset before every single update is slow and memory-hungry; a minibatch — a random, modest-sized slice of the data — gives a noisy but cheap-to-compute estimate of that gradient, and taking many small, noisy steps gets you to a good answer faster than taking few, perfectly accurate ones.

The same thing in PyTorch

import torch
from torch.utils.data import Dataset, DataLoader

class ToyDataset(Dataset):
    def __init__(self, X, y):
        self.X, self.y = X, y

    def __len__(self):
        return len(self.X)              # how many examples total

    def __getitem__(self, idx):
        return self.X[idx], self.y[idx]  # one example, by index

X = torch.randn(1000, 784)     # 1000 fake flattened images
y = torch.randint(0, 10, (1000,))  # 1000 fake labels, classes 0-9

dataset = ToyDataset(X, y)
loader = DataLoader(dataset, batch_size=32, shuffle=True)

for batch_x, batch_y in loader:
    print(batch_x.shape, batch_y.shape)   # torch.Size([32, 784]) torch.Size([32])
    break
Check yourself Why does the DataLoader use shuffle=True during training but you should use shuffle=False for a validation or test loader? Reveal

Shuffling during training stops the model from learning anything about the order examples arrive in (e.g. if all class-0 examples happened to be first) and gives each minibatch a fresh, independent random sample every epoch, which keeps gradient estimates unbiased. For validation or test, you're not updating any weights — you're just measuring performance — so order doesn't affect correctness, and leaving it fixed makes results reproducible and easier to compare run to run.

3The canonical training loop

Intuition first

Every PyTorch training script, no matter how large the model, boils down to the same handful of lines repeated over and over: look at a batch, guess, measure how wrong the guess was, work out how to improve, take a small step in that direction. Below is the whole loop with every line explained — memorize this shape, because you will type some version of it in every project you ever build.

☂ Everyday parallel

Learning to throw darts: throw (forward pass), see how far you missed the bullseye (loss), figure out which way your arm was off and by how much (backward pass), adjust your stance a little (optimizer step), then throw again. Repeat hundreds of times, ideally against many different dartboards, not the same one over and over (that's why we loop over the whole dataset in batches, epoch after epoch).

Now the math

Each step nudges every parameter θ in the model a small amount opposite its gradient, scaled by a learning rate α — the same gradient-descent update from Section 12, just now computed by autograd instead of by hand:

$$ \theta \leftarrow \theta - \alpha \, \nabla_\theta L $$

In words: take each parameter, subtract a small step (learning rate α times its gradient), and that's the update. optimizer.step() below performs exactly this line for every parameter in the model, all at once.

The same thing in PyTorch, annotated

the six lines that train (almost) every PyTorch model

import torch.nn as nn
import torch.optim as optim

model = TinyMLP(in_features=784, hidden=64, out_features=10)
loss_fn = nn.CrossEntropyLoss()          # for multi-class classification -- combines softmax + log-loss
optimizer = optim.Adam(model.parameters(), lr=1e-3)  # Adam: the adaptive optimizer from Section 12

for epoch in range(10):                          # 1. one full pass over the data
    for batch_x, batch_y in loader:              # 2. one minibatch at a time

        optimizer.zero_grad()                    # 3. clear old gradients -- see why below
        y_hat = model(batch_x)                    # 4. forward pass: the model's current guess
        loss = loss_fn(y_hat, batch_y)             # 5. how wrong was the guess? one number
        loss.backward()                            # 6. backward pass: fills in .grad for every parameter
        optimizer.step()                            # 7. nudge every parameter opposite its gradient

    print(f"epoch {epoch}: loss = {loss.item():.4f}")
▲ Why zero_grad() comes first

As you saw in Section 13, calling .backward() adds to whatever gradient is already sitting in .grad — it never overwrites it. Without optimizer.zero_grad() at the top of the loop, each batch's gradient would pile on top of the last batch's, and the optimizer would take a step based on garbage. Clearing the gradients before every forward pass is what makes each step depend only on the current batch.

One line-by-line summary, since this shape repeats forever:

LineWhat it does
optimizer.zero_grad()Resets every parameter's .grad to zero before this batch.
y_hat = model(batch_x)Forward pass — runs forward(), builds the computation graph.
loss = loss_fn(y_hat, batch_y)Compares the guess to the true label, producing one scalar number to minimize.
loss.backward()Backward pass — walks the graph, fills .grad on every parameter.
optimizer.step()Uses each parameter's fresh .grad to update it (Adam's rule, building on plain gradient descent).
Check yourself What would go wrong, concretely, if you swapped the order and called optimizer.step() before loss.backward()? Reveal

optimizer.step() reads whatever is currently sitting in each parameter's .grad and uses it to update the parameter. If you call it before backward() has run for this batch, .grad either holds gradients from a previous batch (if you forgot to zero them) or is empty/zero (if you did zero it), so the update would be based on stale or nonexistent information rather than this batch's actual loss. The order forward → loss → backward → step is not stylistic, it's required — each step's input is the previous step's output.

4GPU basics: same code, different device

Intuition first

A GPU (graphics processing unit) can do the same tensor arithmetic as a CPU, just with thousands of small cores working in parallel instead of a few fast ones — a huge speedup for the kind of bulk matrix multiplication neural networks do constantly. Moving your model to a GPU doesn't change any of the code above; it only changes where the numbers live.

☂ Everyday parallel

A CPU is a few expert chefs who can each cook any dish. A GPU is a thousand line cooks who can each only chop one vegetable — individually limited, but if the job is "chop a thousand carrots," a thousand line cooks obliterate a few expert chefs on time. Matrix multiplication is exactly that kind of job: the same simple operation repeated an enormous number of times.

◆ The one rule that matters

A tensor on the CPU and a tensor on the GPU cannot be combined in one operation — PyTorch will raise an error. The model's parameters and the data you feed it must always live on the same device. Move both, every time.

The same thing in PyTorch

import torch

device = "cuda" if torch.cuda.is_available() else "cpu"

model = TinyMLP(in_features=784, hidden=64, out_features=10)
model.to(device)                 # moves every parameter to the GPU (or leaves it on CPU)

for batch_x, batch_y in loader:
    batch_x = batch_x.to(device)  # data must move too, every batch
    batch_y = batch_y.to(device)

    optimizer.zero_grad()
    y_hat = model(batch_x)         # now both model and data are on `device` -- this works
    loss = loss_fn(y_hat, batch_y)
    loss.backward()
    optimizer.step()
▲ The bug you will hit first

RuntimeError: Expected all tensors to be on the same device, but found at least two devices, cuda:0 and cpu!. This means you moved the model but not the batch (or vice versa). The fix is always the same: find the tensor on the wrong device and add .to(device).

Check yourself You call model.to("cuda") once before training, but inside the loop you forget to move batch_x and batch_y. What happens? Reveal

The forward pass raises a device-mismatch RuntimeError the moment the model's GPU-resident weights try to multiply against the CPU-resident batch. Moving the model once is not enough — every batch of data coming out of the DataLoader starts on the CPU by default and has to be moved explicitly, every single iteration.

5What to carry forward

  • nn.Module is a container: declare layers in __init__, define the computation in forward, and PyTorch finds every parameter for you.
  • Dataset answers "how many, and give me item i"; DataLoader turns that into shuffled minibatches automatically.
  • The training loop is always: zero_grad → forward → loss → backward → step. Zeroing first matters because gradients accumulate.
  • GPU basics: .to(device) moves tensors; model and data must always be on the same device before you combine them.
