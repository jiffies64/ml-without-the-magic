Training at Scale

The gap between a model that trains on paper and one that trains on real hardware, in real time, on real data — normalization, dropout, half-precision numbers, and splitting work across machines.

28 min read You'll learn: batch norm vs layer norm · dropout · mixed precision · gradient accumulation · distributed training

Everything so far has assumed you can just call loss.backward() and optimizer.step() and be done. At real scale, a handful of practical techniques stand between that idea and a model that actually trains stably, fits in memory, and finishes before the deadline. None of it is exotic; all of it is necessary.

◆ The one idea to hold onto

Every technique in this section solves one of two problems: keeping the numbers flowing through the network well-behaved (normalization, dropout, mixed precision), or making the most of limited hardware (gradient accumulation, distributed training). Know which problem you're solving and the right tool is obvious.

1Normalization: the general recipe

Intuition first

As data flows through a deep network, the scale of the numbers at each layer can drift — growing too large, shrinking too small, or shifting off-center — which makes training unstable. Normalization is a layer that resets the numbers back to a well-behaved range (centered around zero, with a controlled spread) at each step, then lets the network relearn whatever scale and offset it actually needs.

☂ Everyday parallel

A sound engineer normalizes every microphone's volume to the same baseline level before a concert, so no one instrument drowns out the others just because it happened to start too loud or too quiet. Then, deliberately, they turn some instruments up and others down to get the mix they actually want. Reset to a common baseline, then re-adjust on purpose — that's normalization.

Now the math

The recipe is always the same two steps: first normalize, then let the network scale and shift the result by its own learned amount.

$$ \begin{aligned} z &= \frac{x - \mu}{\sqrt{\sigma^2 + \epsilon}} \\ y &= \gamma\, z + \beta \end{aligned} $$

In words: μ (mu) is the mean and σ² (sigma-squared) is the variance (how spread out the values are) — subtracting the mean and dividing by the spread gives z, a version of x centered at 0 with spread 1. ε (epsilon) is a tiny constant added purely so we never divide by zero when the variance happens to be 0. Then γ (gamma) and β (beta) are learned numbers that rescale and re-shift the normalized value — they let the network undo the normalization partially or fully if that turns out to be what's best, rather than being stuck with "always centered at 0."

Definition

The only real design choice in any normalization layer is which numbers you average together to compute μ and σ². Batch norm and layer norm are the same formula above, applied over two different groups of numbers.

2Batch norm vs layer norm: which numbers get averaged

Intuition first

Batch normalization computes μ and σ² for each feature separately, averaging across all examples in the mini-batch. Layer normalization computes μ and σ² for each example separately, averaging across all features of that one example. Same formula, one crucial difference: which direction you slice the data to gather statistics from.

☂ Everyday parallel

Batch norm is grading on a curve, per subject: your score on the math test gets adjusted based on how the whole class did on that test — it depends on your classmates. Layer norm is normalizing one student against their own report card: comparing your math score to your own scores in history, art, and gym — it only ever depends on you, never on anyone else in the room.

The same thing in PyTorch

import torch, torch.nn as nn

x = torch.randn(32, 4)   # 32 examples in the batch, 4 features each

bn = nn.BatchNorm1d(num_features=4)
y_bn = bn(x)              # mean/var for each of the 4 features, computed across all 32 examples

ln = nn.LayerNorm(normalized_shape=4)
y_ln = ln(x)              # mean/var for each example, computed across its own 4 features
◆ Why transformers use layer norm

Layer norm's statistics never depend on other examples in the batch, which buys three things transformers (Section 18) need: it works fine with a batch size of 1 (batch norm degenerates there, since a single example gives a variance of essentially zero); it doesn't care that different sequences in a batch have different lengths, since it never mixes examples together; and it behaves identically at training and test time, with no separate "running statistics" bookkeeping that batch norm requires to make evaluation match training.

▲ Watch out

Batch norm needs to behave the same on a single test example as it did on a full training batch, so it tracks a running average of μ and σ² during training and switches to using that running average at evaluation time — which is exactly what model.eval() tells it to do (see Section 15). Layer norm has no such distinction: it computes real statistics from the actual input every single time, train or eval, so there is nothing extra to get wrong.

Check yourself Why does batch normalization behave badly (or fail outright) with a batch size of 1? Reveal

Batch norm computes each feature's mean and variance across the examples in the batch. With only one example, the "mean" of a single number is just that number, and the variance is exactly 0 — the statistics carry no real information about spread, and dividing by sqrt(0 + ε) makes the normalized value dominated entirely by the tiny constant ε, not by anything meaningful in the data. Layer norm is unaffected, because it always has many features within the one example to average over, regardless of how many examples are in the batch.

3Dropout: forcing redundancy

Intuition first

Dropout randomly zeroes out a fraction of a layer's units on every forward pass during training. The network can no longer lean too heavily on any one unit, because that unit might vanish on the very next step — so it's forced to spread the useful signal across many units instead, which reduces overfitting.

☂ Everyday parallel

A sports team that rotates who starts each game, even its best player, ends up with a squad where several players can competently fill any role. If the team only ever depended on one star, losing that player to injury would be catastrophic. Dropout is that rotation policy, applied to a neural network's units instead of a roster.

Now the math

During training, each unit is independently zeroed with probability p, and the survivors are scaled up by 1/(1-p) so the expected total signal stays the same:

$$ \text{dropout}(x_i) = \begin{cases} 0 & \text{with probability } p \\ \dfrac{x_i}{1-p} & \text{with probability } 1-p \end{cases} $$

In words: flip a biased coin for every unit. Heads (chance p): that unit outputs 0 this step. Tails: the unit's value is divided by 1 − p to make up for the units that got zeroed, so the layer's total output stays roughly the same size on average whether or not dropout is active. This rescaling is called inverted dropout, and it's what lets dropout be a no-op at test time with zero extra work.

The same thing in PyTorch

drop = nn.Dropout(p=0.5)

model.train()
y = drop(x)     # roughly half the entries become 0; survivors are doubled (1/(1-0.5))

model.eval()
y = drop(x)     # identity -- dropout does nothing at eval time, x passes through unchanged
Check yourself You forgot to call model.eval() before running validation. Predictions come out worse than expected and change slightly every time you re-run the same input. Why, specifically? Reveal

In training mode, dropout is still active: each forward pass zeroes a different random subset of units, so the same input produces a different, noisier output every call — and you're effectively evaluating with a random, incomplete slice of the network rather than the full model. Calling model.eval() turns dropout into the identity function, so every unit contributes every time, giving stable, deterministic, and stronger predictions.

4Mixed precision: same math, half the bits

Intuition first

Every number in a network is normally stored as a 32-bit float (fp32). Modern GPUs can run much faster, and store roughly twice as much in memory, using a 16-bit format instead — either fp16 or bf16 (two different ways of packing a number into 16 bits). Mixed precision training runs most of the network's math in 16-bit numbers while keeping a few sensitive spots — like the master copy of the weights — in 32-bit, to get the speed without losing correctness.

☂ Everyday parallel

A tailor doesn't measure every cut to the nearest micrometer — a millimeter of precision is plenty for cloth, and using a coarser tool is faster and cheaper. But for one critical piece, like fitting a watch gear, they switch back to the precise tool. Mixed precision is using the coarser, faster measurement everywhere it's safe, and the precise one only where it truly matters.

Now the math: why loss scaling exists

fp16 can represent numbers only within a much narrower range than fp32 before rounding them to zero. Many gradients during training are legitimately tiny — say, 1e-8 — and a value that small can underflow in fp16 (round down to exactly 0.0), silently deleting a real gradient. Loss scaling fixes this with one multiplication and one division:

$$ \text{scaled\_loss} = s \cdot L, \qquad \nabla_{\text{used}} = \frac{1}{s}\,\nabla(\text{scaled\_loss}) $$

In words: multiply the loss L by a large scale factor s (e.g. 1024 or higher) before calling backward(). By the chain rule, every gradient computed from that scaled loss is also multiplied by s, which pushes tiny gradients up out of the underflow zone and into a range fp16 can represent. Right before the optimizer uses them, divide back by the same s so the actual weight update is correct. bf16 has the same exponent range as fp32 (it just drops precision, not range), so it rarely needs this trick at all.

The same thing in PyTorch

scaler = torch.cuda.amp.GradScaler()

for xb, yb in loader:
    optimizer.zero_grad()
    with torch.cuda.amp.autocast(dtype=torch.float16):
        out = model(xb)
        loss = criterion(out, yb)

    scaler.scale(loss).backward()   # scale the loss up before backward
    scaler.step(optimizer)          # unscales gradients, then steps (skips the step if any are inf/NaN)
    scaler.update()                 # adjusts the scale factor for the next iteration
Check yourself A gradient of 3e-8 is a real, non-zero value in fp32 but becomes exactly 0.0 in fp16. What does loss scaling do about it, mechanically? Reveal

Loss scaling multiplies the loss by a large constant s before backward() runs, so by the chain rule every downstream gradient — including this one — is also multiplied by s. A gradient of 3e-8 × 1024 ≈ 3e-5 is comfortably inside fp16's representable range and no longer rounds to zero. After backward(), the scaled gradients are divided by s again before the optimizer applies them, so the final weight update is mathematically the same as if you'd never scaled anything — you only used the scaling to survive the trip through 16-bit storage.

5Gradient accumulation: a bigger batch on smaller memory

Intuition first

Sometimes the batch size you want doesn't fit in GPU memory. Gradient accumulation fakes a large batch by processing several small "micro-batches" one at a time, adding up their gradients without resetting them, and only calling optimizer.step() once every few micro-batches — as if all of them had been one big batch all along.

☂ Everyday parallel

You want to deposit 400 dollars but your wallet only holds 100 at a time. You make four trips to the ATM, but you don't deposit each 100 separately into different sub-accounts — you add them up and it's exactly as if you'd deposited 400 once. Gradient accumulation is four small trips that add up to the one big deposit you actually wanted.

The same thing in PyTorch

accumulation_steps = 4        # 4 micro-batches of 32 == an effective batch of 128
optimizer.zero_grad()

for i, (xb, yb) in enumerate(loader):
    out = model(xb)
    loss = criterion(out, yb) / accumulation_steps   # average, not sum, across micro-batches
    loss.backward()                                   # gradients ACCUMULATE in .grad (no zero_grad yet)

    if (i + 1) % accumulation_steps == 0:
        optimizer.step()
        optimizer.zero_grad()
▲ Watch out

Dividing the loss by accumulation_steps is not optional. Skip it and four accumulated micro-batch gradients add up to roughly 4× the gradient a true batch of 128 would have produced — which behaves like secretly training with a 4× larger learning rate, and can destabilize training in a way that looks like an unrelated bug.

Check yourself You accumulate gradients over 4 micro-batches of size 32 but forget to divide the loss by 4. How does this actually change what the optimizer does, compared to a true batch of 128? Reveal

A true batch of 128 with a mean-reduced loss produces one gradient that's the average over 128 examples. Without dividing, summing 4 un-averaged micro-batch losses (each already averaged over its own 32) produces a gradient that's roughly 4x too large before the optimizer step. The optimizer then applies an update as if the learning rate were 4x higher than configured — which can cause instability or divergence that has nothing to do with the model itself, only with this missing division.

6Distributed training: an honest overview

Intuition first

When a model or dataset is too large for one machine, the work is split across several. There is no single "distributed training" technique — there are a few different things you can split, and real systems often combine them. None of it is magic: it all costs communication between machines, and that communication is usually the actual bottleneck, not the computation.

☂ Everyday parallel

A restaurant kitchen with one overloaded chef can add more chefs. You could give each chef an identical copy of the full menu and have them each cook different tables' orders (data parallelism). Or you could have one chef only do sauces and hand plates to a chef who only does grilling, in a chain (pipeline parallelism). Either way, the moment plates need to move between chefs is the moment things can slow down — coordination has a cost.

Data parallelism, the workhorse

The most common setup by far is data parallelism: every device (GPU) holds a full, identical copy of the model. Each device processes a different slice of the data and computes its own gradients independently. Then, before anyone updates their weights, all devices combine their gradients with an all-reduce — a collective operation where every device ends up with the same combined (typically averaged) gradient — so every replica applies an identical update and stays in sync.

  • Model / tensor parallelism — the model itself is too big to fit on one device, so individual layers, or even individual matrices within a layer, are split across devices, and a single forward pass requires those devices to exchange intermediate results.
  • Pipeline parallelism — different layers of the model live on different devices, and data flows through them like a factory assembly line, with each device handing its output to the next.
◆ The honest bottleneck

Adding devices doesn't automatically make training proportionally faster. Every one of these strategies requires devices to send data to each other — gradients in data parallelism, activations in tensor and pipeline parallelism — over a network that is almost always slower than the computation itself. Past a certain scale, training speed is limited by how fast machines can talk to each other, not by how fast any one of them can compute. This is why hardware interconnect (the physical links between devices) matters as much as raw compute in large-scale training.

7What to carry forward

  • Every normalization layer is normalize, then scale-and-shift: $y = \gamma(x-\mu)/\sqrt{\sigma^2+\epsilon} + \beta$. The only difference between variants is which numbers μ and σ² are computed over.
  • Batch norm normalizes each feature across the batch (depends on other examples); layer norm normalizes each example across its own features (independent of the batch) — which is why transformers use layer norm.
  • Dropout randomly zeroes units during training to prevent over-reliance on any one of them, and is switched off entirely by model.eval().
  • Mixed precision trades numeric range for speed and memory; loss scaling keeps tiny fp16 gradients from rounding to zero.
  • Gradient accumulation simulates a large batch on limited memory by summing (averaged) micro-batch gradients before one optimizer step.
  • Distributed training splits either the data (data parallelism) or the model itself (model/tensor/pipeline parallelism) across devices — and communication between devices, not raw compute, is usually the real limiting factor.
