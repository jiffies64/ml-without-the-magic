Training at Scale

What changes when a model trains on real hardware, in real time, on real data: normalization, dropout, half-precision numbers, and splitting work across machines.

28 min read
You'll learn
  • batch norm vs layer norm
  • dropout
  • mixed precision
  • gradient accumulation
  • distributed training

So far we assumed you can call loss.backward() and optimizer.step() and be done. At real scale, you need a few practical techniques more. They make the model train stably, fit in memory, and finish in time. None of them is exotic, and all of them are necessary.

◆ The one idea to hold onto

Every technique in this section solves one of two problems. Some keep the numbers flowing through the network well-behaved (normalization, dropout, mixed precision). Others make the most of limited hardware (gradient accumulation, distributed training). Know which problem you are solving, and the right tool follows.

1Normalization: the general recipe

Intuition first

As data flows through a deep network, the scale of the numbers at each layer can drift. They can grow too large, shrink too small, or move off center, and this makes training unstable. Normalization is a layer that brings the numbers back to a well-behaved range: centered around zero, with a controlled spread. Then it lets the network learn whatever scale and offset it needs.

☂ Everyday parallel

A sound engineer first sets every microphone to the same baseline level before a concert. So no instrument is too loud only because it started too loud. Then the engineer turns some instruments up and others down on purpose, to get the mix they want. Reset to a common baseline, then adjust on purpose: that is normalization.

Now the math

The recipe is always the same two steps: first normalize, then let the network scale and shift the result by its own learned amount.

$$ \begin{aligned} z &= \frac{x - \mu}{\sqrt{\sigma^2 + \epsilon}} \\ y &= \gamma\, z + \beta \end{aligned} $$

In words: $\mu$ (mu) is the mean and $\sigma^2$ (sigma squared) is the variance, which measures how spread out the values are. Subtracting the mean and dividing by the standard deviation $\sigma$ gives $z$: a version of $x$ with mean 0 and spread 1. $\epsilon$ (epsilon) is a tiny constant, for example $10^{-5}$, so we never divide by zero. Then $\gamma$ (gamma) and $\beta$ (beta) are learned numbers that rescale and shift the normalized value. They let the network undo the normalization, partly or fully, if that works better. With $\gamma = \sigma$ and $\beta = \mu$ (ignoring $\epsilon$), the layer gives back $x$ exactly.

Definition

The only real design choice in a normalization layer is which numbers you average together to compute $\mu$ and $\sigma^2$. Batch norm and layer norm use the same formula above, over two different groups of numbers.

Check yourself A layer outputs the values $2, 4, 6$. Normalize them with $\epsilon = 0$, $\gamma = 1$, $\beta = 0$. Then say what changes if $\gamma = 3$ and $\beta = 1$. Reveal

The mean is $\mu = 4$. The variance is $\sigma^2 = (4 + 0 + 4)/3 = 8/3$, so $\sigma \approx 1.63$. Then $z \approx (-1.22, 0, 1.22)$. With $\gamma = 3$ and $\beta = 1$, the output is $y = 3z + 1 \approx (-2.67, 1, 4.67)$. The normalization fixed the scale; the learned $\gamma$ and $\beta$ then chose a new one.

2Batch norm vs layer norm: which numbers get averaged

Intuition first

Batch normalization computes $\mu$ and $\sigma^2$ for each feature separately. It averages across all examples in the mini-batch. Layer normalization computes $\mu$ and $\sigma^2$ for each example separately. It averages across all features of that one example. The formula is the same; the difference is the direction in which you slice the data.

☂ Everyday parallel

Batch norm is grading on a curve, per subject. Your math score is adjusted by how the whole class did on that test, so it depends on your classmates. Layer norm compares one student with their own report card: your math score against your own scores in history, art, and sports. It depends only on you, never on anyone else in the room.

The same thing in PyTorch

batch norm vs layer norm on the same batch

import torch, torch.nn as nn

torch.manual_seed(0)
x = torch.randn(32, 4)   # 32 examples in the batch, 4 features each

bn = nn.BatchNorm1d(num_features=4)
y_bn = bn(x)              # mean/var for each of the 4 features, across all 32 examples

ln = nn.LayerNorm(normalized_shape=4)
y_ln = ln(x)              # mean/var for each example, across its own 4 features

print(y_bn.std(dim=0, correction=0))      # tensor([1.0000, 1.0000, 1.0000, 1.0000], ...)
print(y_ln.std(dim=1, correction=0)[:3])  # tensor([1.0000, 1.0000, 1.0000], ...)

In words: after batch norm, each column (feature) has spread 1. After layer norm, each row (example) has spread 1. Both means are 0 in the same directions. (The ... stands for the grad_fn part of the printout.)

◆ Why transformers use layer norm

Layer norm's statistics never depend on other examples in the batch. This gives transformers (Section 18) three things they need:

  • It works with a batch size of 1. Batch norm cannot train there, because one example has no spread across the batch.
  • It does not care that sequences in a batch have different lengths, because it never mixes examples.
  • It behaves the same at training and test time. Batch norm needs extra “running statistics” for evaluation to match training.
▲ Watch out

At test time, batch norm may see a single example, but it must still behave as in training. So during training it keeps a running average of $\mu$ and $\sigma^2$. At evaluation time it uses that running average instead of batch statistics. This is what model.eval() switches on (see Section 15). Layer norm has no such difference. It computes its statistics from the actual input every time, in training and in evaluation, so there is nothing extra to get wrong.

Check yourself You call nn.BatchNorm1d(4) in training mode on a batch of shape (1, 4). What would the formula give, and what does PyTorch do? Reveal

With one example, each feature's mean is that single value, so $x - \mu = 0$ exactly and the variance is 0. The normalized value is $z = 0/\sqrt{\epsilon} = 0$, so every output would be $\beta$, whatever the input was. The layer would carry no information. PyTorch refuses to do this and raises ValueError: Expected more than 1 value per channel when training. In eval() mode it works, because it uses the running statistics. Layer norm has no problem: it averages over the 4 features of the one example.

3Dropout: forcing redundancy

Intuition first

Dropout randomly sets a fraction of a layer's units to zero on every forward pass during training. The network cannot depend too much on any one unit, because that unit may be gone on the next step. So it must spread the useful signal across many units, and this reduces overfitting.

☂ Everyday parallel

A sports team that rotates who starts each game, even its best player, gets a squad where several players can fill any role. A team that always depends on one star is in trouble when that player is injured. Dropout is that rotation policy, applied to the units of a neural network.

Now the math

During training, each unit is set to zero with probability $p$, independently of the others. The surviving units are scaled up by $1/(1-p)$, so the expected value stays the same:

$$ \text{dropout}(x_i) = \begin{cases} 0 & \text{with probability } p \\ \dfrac{x_i}{1-p} & \text{with probability } 1-p \end{cases} $$

In words: flip a biased coin for every unit. With chance $p$ the unit outputs 0 this step. Otherwise its value is divided by $1 - p$ to make up for the zeroed units. The expected output is then $p \cdot 0 + (1-p) \cdot x_i/(1-p) = x_i$, the same as without dropout. This rescaling is called inverted dropout. Because of it, dropout can do nothing at test time, with no extra work.

The same thing in PyTorch

dropout in training mode and in eval mode

import torch, torch.nn as nn

torch.manual_seed(0)
drop = nn.Dropout(p=0.5)
x = torch.ones(8)

drop.train()    # inside a model, model.train() does this for every layer
print(drop(x))  # tensor([0., 0., 2., 0., 0., 0., 2., 2.])  survivors doubled: 1/(1-0.5)

drop.eval()     # inside a model, model.eval() does this
print(drop(x))  # tensor([1., 1., 1., 1., 1., 1., 1., 1.])  identity at eval time

In words: in training mode each entry becomes 0 or 2. Here 3 of 8 survived; on average half do. In eval mode the layer passes $x$ through unchanged. When dropout sits inside a model, model.train() and model.eval() set this mode for all its layers.

Check yourself Someone writes their own dropout: in training it zeros each unit with $p = 0.5$ but does not divide by $1 - p$. In eval it passes $x$ through. What goes wrong at test time, and how would you fix it without changing training? Reveal

In training, the next layer sees inputs whose expected value is $0.5\,x$, and it learns weights for that scale. At test time it suddenly gets $x$, twice as large on average, so its outputs are off. One fix is to multiply by $1 - p = 0.5$ at test time (this is the original, non-inverted dropout). Inverted dropout moves that factor into training instead, so evaluation needs no change.

4Mixed precision: same math, half the bits

Intuition first

Every number in a network is normally stored as a 32-bit float (fp32). Modern GPUs run much faster with a 16-bit format, and they can store about twice as many numbers in the same memory. There are two common 16-bit formats, fp16 and bf16, which divide the 16 bits in different ways. Mixed precision training runs most of the math in 16 bits. It keeps a few sensitive parts in 32 bits, such as the master copy of the weights. You get the speed without losing correctness.

☂ Everyday parallel

A shop rounds each receipt to the whole dollar, but it keeps the account balance to the cent. Rounding receipts is fast and good enough. But suppose the balance itself were kept in whole dollars: a purchase of 40 cents would round to zero and vanish, again and again. Mixed precision works the same way. The forward and backward math uses 16 bits (the receipts), while the master weights stay in fp32 (the balance). Many small updates can then still add up.

You can see that last point directly. In fp16, the numbers near 1.0 are about 0.001 apart. So 1.0 + 1e-4 rounds back to 1.0, and a small weight update is lost. In fp32 it gives 1.0001.

Now the math

fp16 has only 5 exponent bits, so its range is narrow. Its largest value is 65,504. Its smallest normal value is $2^{-14} \approx 6.1 \times 10^{-5}$. Below that, fp16 has subnormal numbers, which reach down to $2^{-24} \approx 6 \times 10^{-8}$ but with fewer significant digits. Anything smaller underflows: it rounds to exactly 0. Many gradients during training are this small, for example $10^{-8}$. In fp16 such a gradient becomes 0, and a real gradient is lost without any warning. Loss scaling fixes this with one multiplication and one division:

$$ L_{\text{scaled}} = s \cdot L, \qquad \nabla_{\text{used}} = \frac{1}{s}\,\nabla L_{\text{scaled}} $$

In words: multiply the loss $L$ by a large scale factor $s$ (for example $2^{16} = 65536$) before calling backward(). By the chain rule, every gradient computed from the scaled loss is also multiplied by $s$. This moves tiny gradients out of the underflow zone into the range fp16 can store. Before the optimizer uses them, divide by the same $s$ in fp32, so the weight update is correct. The format bf16 has the same exponent range as fp32 (it drops precision, not range), so it rarely needs this trick.

The same thing in PyTorch

underflow and loss scaling, checked on the CPU

import torch

g = torch.tensor(1e-8)                     # a small but real fp32 gradient
print(g.half())                            # tensor(0., dtype=torch.float16)  underflow
s = 65536.0                                # loss scale, 2**16
print((g * s).half())                      # tensor(0.0007, dtype=torch.float16)  safe
print((g * s).half().float() / s)          # tensor(9.9972e-09)  unscaled in fp32
print(g.bfloat16())                        # tensor(1.0012e-08, dtype=torch.bfloat16)

w = torch.tensor(1.0, dtype=torch.float16)
print(w + torch.tensor(1e-4, dtype=torch.float16))   # tensor(1., dtype=torch.float16)  lost
print(torch.tensor(1.0) + 1e-4)                      # tensor(1.0001)  kept in fp32

In a real training loop, PyTorch does the scaling for you. The loop below assumes a CUDA GPU and the model, optimizer, criterion, and loader from Section 14.

a mixed-precision training loop with a gradient scaler

scaler = torch.amp.GradScaler("cuda")     # starts with s = 65536 and adapts it

for xb, yb in loader:
    optimizer.zero_grad()
    with torch.autocast("cuda", dtype=torch.float16):   # run the forward pass in fp16 where safe
        out = model(xb)
        loss = criterion(out, yb)

    scaler.scale(loss).backward()   # scale the loss up before backward
    scaler.step(optimizer)          # unscales gradients, then steps (skips the step if any are inf/NaN)
    scaler.update()                 # adjusts the scale factor for the next iteration

In words: autocast runs each operation in fp16 when that is safe and in fp32 when it is not. The weights themselves stay in fp32. If a scaled gradient overflows to inf, the scaler skips that step and lowers $s$. If many steps go well, it raises $s$ again. With dtype=torch.bfloat16 you can usually drop the scaler.

Check yourself A gradient is $3 \times 10^{-8}$. What does fp16 store for it? And what happens if you use a scale of only $s = 1024$? Reveal

It does not become 0. It rounds to the smallest fp16 subnormal, $2^{-24} \approx 5.96 \times 10^{-8}$, which is about twice the true value. So the gradient is kept, but with a large error. With $s = 1024$ the scaled value is about $3.1 \times 10^{-5}$. That is still below the smallest normal value $6.1 \times 10^{-5}$, so it is subnormal and has only a few correct digits. A larger scale such as 65536 moves it to about $2 \times 10^{-3}$, fully in the normal range. After backward() the gradients are divided by $s$ again, so the update is the same as without scaling.

5Gradient accumulation: a bigger batch on smaller memory

Intuition first

Sometimes the batch size you want does not fit in GPU memory. Gradient accumulation builds a large batch from several small micro-batches. It processes them one at a time and adds up their gradients without resetting them. It calls optimizer.step() only once every few micro-batches, as if they were all one big batch.

☂ Everyday parallel

You survey 128 people, but your room holds only 32 at a time. So you run four sessions. To get the average answer of all 128, you add the four session averages and divide by 4. If you forget to divide, you report 4 times the true average. Gradient accumulation is the same: each micro-batch loss is already an average, so you divide it by the number of micro-batches.

Now the math

Split a batch of $N$ examples into $M$ micro-batches of $N/M$ examples each. Let $L_m$ be the mean loss of micro-batch $m$. The mean loss of the full batch is then the mean of the micro-batch means:

$$ L = \frac{1}{N}\sum_{n=1}^{N} \ell_n = \frac{1}{M}\sum_{m=1}^{M} \underbrace{\frac{M}{N}\sum_{n \in m} \ell_n}_{L_m} = \sum_{m=1}^{M} \frac{L_m}{M} $$

In words: $\ell_n$ is the loss of example $n$. Because gradients add up, $\nabla L = \sum_m \nabla (L_m / M)$. So if each micro-batch calls backward() on $L_m / M$, the summed .grad is exactly the gradient of one full batch.

The same thing in PyTorch

four micro-batches give the same gradient as one batch of 128

import torch, torch.nn as nn

torch.manual_seed(0)
model = nn.Linear(10, 1)
criterion = nn.MSELoss()
X, Y = torch.randn(128, 10), torch.randn(128, 1)

# (a) one true batch of 128
model.zero_grad()
criterion(model(X), Y).backward()
g_full = model.weight.grad.clone()

# (b) 4 micro-batches of 32, each loss divided by 4
accumulation_steps = 4
model.zero_grad()
for xb, yb in zip(X.split(32), Y.split(32)):
    loss = criterion(model(xb), yb) / accumulation_steps
    loss.backward()                      # gradients ADD UP in .grad (no zero_grad yet)
g_acc = model.weight.grad.clone()

print(torch.allclose(g_full, g_acc, atol=1e-6))                 # True
print((g_acc * accumulation_steps).norm() / g_full.norm())      # tensor(4.)  without the division

In words: the accumulated gradient matches the full-batch gradient. Without the division it would be 4 times larger. In a real loop you call optimizer.step() and optimizer.zero_grad() once every accumulation_steps micro-batches, for example with if (i + 1) % accumulation_steps == 0:.

▲ Watch out

Dividing the loss by accumulation_steps is not optional. Without it, four accumulated micro-batch gradients add up to 4 times the gradient of a true batch of 128. With plain SGD this acts like a 4 times larger learning rate. It can make training unstable in a way that looks like an unrelated bug.

Check yourself You forget to divide by 4, but your optimizer is Adam, not SGD. Does the mistake still matter as much? Reveal

Much less. Adam divides each gradient by a running estimate of its own size (Section 12). If every gradient is 4 times larger, that estimate is also 4 times larger, and the ratio is almost unchanged. Only the small $\epsilon$ in the denominator breaks the cancellation. In a quick test, three Adam steps moved the weights by the same amount with and without the factor 4, while SGD moved them about twice as far. It is still a bug: gradient clipping, weight decay, and logged gradient norms all see the wrong size.

6Distributed training: an overview

Intuition first

When a model or dataset is too large for one machine, the work is split across several. There is no single “distributed training” technique. You can split different things, and real systems often combine several splits. Every split costs communication between devices, and that communication is often the real limit, not the computation.

☂ Everyday parallel

A school must grade a large stack of exams. It can give each teacher the same answer key and a different pile of exams (data parallelism). Or each teacher can grade only one page and pass the exam to the next teacher (pipeline parallelism). Either way, the teachers must coordinate: meet to combine notes, or wait for the exam from the previous teacher. That coordination costs time.

Data parallelism, the most common setup

In data parallelism, every device (GPU) holds a full copy of the model. Each device processes a different slice of the data and computes its own gradients. Then, before any weights change, all devices combine their gradients with an all-reduce. An all-reduce is a group operation after which every device holds the same combined (usually averaged) gradient. So every copy applies the same update and the copies stay the same. With 4 GPUs of 32 examples each, this is the gradient of one batch of 128, as in gradient accumulation.

A full copy on every GPU wastes memory. With Adam, each parameter also needs two optimizer values and a gradient. Sharded data parallelism fixes this: each GPU stores only its share of the weights, gradients, and optimizer state, and collects the rest when it needs them. This is ZeRO (from DeepSpeed) and FSDP (Fully Sharded Data Parallel, in PyTorch).

When the model itself is split, there are other options:

  • Tensor parallelism: single layers, or even single matrices, are split across devices. One forward pass then needs those devices to exchange intermediate results.
  • Pipeline parallelism: different layers live on different devices. Data flows through them like an assembly line, and each device passes its output to the next.
  • Expert parallelism: in a mixture-of-experts model, different experts live on different devices, and each token is sent to the device of its expert (Section 22).
◆ The real bottleneck

Adding devices does not automatically make training proportionally faster. Every strategy needs devices to send data to each other: gradients in data parallelism, activations in tensor and pipeline parallelism. The links between devices are usually slower than the computation. Past a certain scale, training speed depends on how fast devices can communicate, not on how fast each one computes. This is why the interconnect (the physical links between devices) matters as much as raw compute in large-scale training.

Check yourself A model fits on one GPU for inference but runs out of memory in training with Adam. You have 8 GPUs. Does plain data parallelism help? What would? Reveal

Plain data parallelism does not help with memory. Every GPU still holds the full weights, gradients, and Adam state, so each one runs out of memory the same way. It only helps with speed. Sharded data parallelism (FSDP or ZeRO) does help. Each of the 8 GPUs stores about one eighth of the gradients and optimizer state (and, in the full version, of the weights). Smaller micro-batches with gradient accumulation also reduce activation memory.

7What to carry forward

  • Every normalization layer is normalize, then scale and shift: $$y = \gamma\,\frac{x-\mu}{\sqrt{\sigma^2+\epsilon}} + \beta.$$ The only difference between variants is which numbers $\mu$ and $\sigma^2$ are computed over.
  • Batch norm normalizes each feature across the batch (it depends on other examples). Layer norm normalizes each example across its own features (it is independent of the batch), which is why transformers use layer norm.
  • Dropout randomly zeros units during training so the network does not depend on any one of them. model.eval() switches it off.
  • Mixed precision trades precision (and, for fp16, range) for speed and memory. Loss scaling keeps tiny fp16 gradients from rounding to zero, and fp32 master weights keep small updates.
  • Gradient accumulation builds a large batch on limited memory by summing micro-batch gradients, each divided by the number of micro-batches, before one optimizer step.
  • Distributed training splits the data (data parallelism, optionally sharded with FSDP or ZeRO) or the model (tensor, pipeline, or expert parallelism) across devices. Communication between devices, not raw compute, is often the real limit.
